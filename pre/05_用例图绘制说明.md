# 用例图绘制说明

本文件只给出手工绘图所需的参与者、用例、关系和布局，不直接生成图。推荐先画一张“总览用例图”，再准备一张“AI 分析子用例图”作为备份页。

## 1. 总览用例图

### 1.1 系统边界

- 边界框标题：`校园多源消息智能聚合与信息管理系统（UniBrief）`
- 边界框内只放系统提供的用例。
- MySQL、FastAPI、React 不画成参与者，它们是内部实现。

### 1.2 参与者

| 编号 | 参与者 | 类型 | 与系统的关系 |
|---|---|---|---|
| A1 | 系统使用者/信息管理者 | 主参与者 | 发起管理、导入、分析、查询、修正、统计等操作 |
| A2 | 消息导入适配器 | 外部系统 | 向系统提供统一格式的 JSON/CSV 消息 |
| A3 | OpenAI-compatible AI 服务 | 外部系统 | 提供模型列表、连接测试和真实消息分析 |

不画“管理员”“普通用户”等角色，因为项目明确为单用户系统。

### 1.3 主用例

| 编号 | 用例名称 | 主参与者 | 简要目标 |
|---|---|---|---|
| UC01 | 管理消息平台 | A1 | 新建、查看 Platform |
| UC02 | 管理消息渠道 | A1 | 新建、查看、修改 Channel |
| UC03 | 导入消息 | A1、A2 | 批量导入统一格式消息并返回结果 |
| UC04 | 查询原始消息 | A1 | 分页、筛选、查看原文和处理状态 |
| UC05 | 配置与选择 AI 模型 | A1 | 查看安全配置、加载列表或手工输入模型 ID |
| UC06 | 测试 AI 连接 | A1、A3 | 验证 Base URL、Key 和选定模型 |
| UC07 | 分析单条消息 | A1、A3 | 对一个 Message 使用选定模型分析 |
| UC08 | 批量分析消息 | A1、A3 | 对一批 Message 使用同一选定模型分析 |
| UC09 | 浏览与筛选有效信息 | A1 | 按分类、标签、重要度、状态等查询 |
| UC10 | 查看信息详情与来源 | A1 | 查看摘要、分类、标签、Event 及关联原文 |
| UC11 | 人工修正/归档信息 | A1 | 修改标题、摘要、重要度和状态 |
| UC12 | 查看事项 | A1 | 按状态、时间范围查看 Event |
| UC13 | 查看统计 | A1 | 查看渠道有效率、分类分布、热门标签等 |

### 1.4 建议的 include / extend 关系

主图不要塞入所有内部处理，只保留能帮助理解的关系：

| 来源用例 | 关系 | 目标用例 | 理由 |
|---|---|---|---|
| UC03 导入消息 | `<<include>>` | 校验统一消息格式 | 每次导入都必须执行 |
| UC03 导入消息 | `<<include>>` | 消息去重 | 每次导入都必须执行 |
| UC07 分析单条消息 | `<<include>>` | 指定 AI 模型 | 没有本次模型且无默认模型时不能分析 |
| UC08 批量分析消息 | `<<include>>` | 指定 AI 模型 | 同上 |
| 手工输入模型 ID | `<<extend>>` | UC05 配置与选择 AI 模型 | 当模型列表不支持或用户需要其他模型时触发 |
| UC10 查看信息详情与来源 | `<<include>>` | 追溯原始消息 | 信息详情必须能看到来源证据 |
| UC09 浏览与筛选有效信息 | `<<include>>` | 搜索与组合筛选 | 浏览信息的核心能力 |

“生成 Event”属于分析后的条件业务，可在 AI 子用例图中作为 `<<extend>>`，不建议在总览图里再增加一条很长的线。

### 1.5 手工布局

建议使用横向 16:9 页面：

- 左侧上方放 A2 消息导入适配器，只连接 UC03。
- 左侧中部放 A1 系统使用者，作为主参与者。
- 右侧中部放 A3 AI 服务，连接 UC06、UC07、UC08，也可连接“加载模型列表”子用例。
- 系统边界内按三列放用例：
  - 左列：UC01、UC02、UC03、UC04；
  - 中列：UC05、UC06、UC07、UC08；
  - 右列：UC09、UC10、UC11、UC12、UC13。
- A1 可用一条总线式折线连接各列，避免十几条斜线交叉。
- `<<include>>` 和 `<<extend>>` 使用统一虚线箭头，并在图例写明方向。

### 1.6 图旁结论

图右下角保留一句话：

> 单用户并不等于单一功能；系统仍需协调消息适配器与真实 AI 服务，完成从导入到查询统计的完整业务闭环。

## 2. AI 分析子用例图

这张图建议放在备份页，老师追问 AI 如何落库时使用。

### 2.1 参与者

- A1 系统使用者
- A3 OpenAI-compatible AI 服务

### 2.2 用例

| 编号 | 用例 | 关系建议 |
|---|---|---|
| AUC01 | 查看安全 AI 配置 | 独立用例 |
| AUC02 | 选择 AI 模型 | `<<include>>` 加载模型列表，模型列表由 A3 提供 |
| AUC03 | 手工输入模型 ID | `<<extend>>` AUC02，条件为列表不支持或用户指定其他模型 |
| AUC04 | 测试模型连接 | 与 A3 关联，`<<include>>` 指定模型 |
| AUC05 | 单条分析 | 与 A3 关联，`<<include>>` 指定模型、校验 AI 输出、持久化结果 |
| AUC06 | 批量分析 | 与 A3 关联，`<<include>>` 指定模型；可复用单条分析逻辑 |
| AUC07 | 识别无用消息 | 分析结果分支 |
| AUC08 | 创建/关联/更新信息 | 分析结果分支 |
| AUC09 | 生成分类与标签 | `<<include>>` AUC08 |
| AUC10 | 生成 Event | `<<extend>>` AUC08，条件为识别到时间属性 |
| AUC11 | 失败后更换模型重试 | `<<extend>>` AUC05/AUC06 |

### 2.3 注意事项

- “严格校验 AI 输出”虽然通常是内部步骤，但在子图中保留，能解释为什么模型文本不会直接污染数据库。
- 不画 MockAIProvider；合成消息输入与真实 AI 服务不冲突。
- 不把“AI 自动决定一切”作为用例名称，应明确最终落到创建、关联或更新 InformationItem。

## 3. 关键用例规约

### UC03 导入消息

- 前置条件：消息符合统一 Adapter 输入格式；平台与渠道信息可识别。
- 主成功场景：用户选择文件 -> 系统校验 -> 归一化来源 -> 检查唯一键 -> 写入新 Message -> 返回新增/重复/失败数。
- 备选场景：格式错误时拒绝该记录并说明字段；重复消息跳过；批次部分失败时返回逐项结果。
- 后置条件：新 Message 为 PENDING，重复消息数量不增加。

### UC07 分析单条消息

- 前置条件：Message 存在且有可用模型 ID；服务端已配置 API Key。
- 主成功场景：标记 PROCESSING -> 查询候选 InformationItem -> 调用真实 AI -> 校验输出 -> 保存 AIAnalysis -> 创建/关联/更新信息及关系 -> 更新状态。
- 备选场景：无用消息保存分析并设为 IGNORED；AI 或数据库失败时设为 FAILED 并允许重试。
- 后置条件：原始 Message 始终存在；成功时所有业务结果原子提交。

### UC10 查看信息详情与来源

- 前置条件：InformationItem 存在。
- 主成功场景：返回标题、摘要、重要度、状态、分类、标签、Event 和关联 Message。
- 备选场景：无 Event 时正常显示“无时间事项”；来源为空应视为数据质量问题，而不是普通业务状态。
- 后置条件：不修改数据。

### UC13 查看统计

- 前置条件：无。
- 主成功场景：加载渠道有效率、分类分布、热门标签和可选截止事项。
- 备选场景：无数据时返回零值或空集合并显示空状态。
- 后置条件：不修改数据，统计口径可由数据库查询复核。

## 4. 绘图自检

- 是否只有三类外部参与者，没有把数据库或框架画成演员？
- 是否清楚表现单用户边界？
- 是否包含导入、AI、信息、事项、统计和来源追溯？
- `include` 箭头是否指向被包含用例，`extend` 是否指向被扩展用例？
- 是否避免在总览图中放入二十多个内部步骤？
- 是否没有出现运行时 Mock AI、登录或权限管理？
