# 多用户版分模块用例图与 ER 图绘制说明

本文只提供手工绘图所需的节点、关系、布局和讲解重点，不直接生成图片。

## 1. 统一图例

- ER 实体框只写英文表名。
- 关系使用 Crow's Foot：`1`、`0..1`、`0..N`、`1..N`。
- User 表示登录用户；Sender 表示外部群聊发送者。
- 全局实体使用一种颜色，用户私有实体使用另一种颜色，关联表使用中性色。
- SystemSetting 属于系统配置域，不与普通业务表建立外键。

## 2. 模块一用例图：用户、来源与原始消息

参与者：
- 普通用户
- 系统管理员
- 消息导入适配器

用例：
- 管理员登录
- 创建/启停用户、重置密码
- 开关公开注册
- 管理 Platform、Category
- 普通用户注册（仅开关启用时）
- 普通用户登录/退出/修改密码
- 管理 Channel
- 导入 Message
- 校验格式
- 消息去重
- 查询原始 Message

关系：
- 导入 Message `<<include>>` 校验格式、消息去重。
- 普通用户注册 `<<extend>>` 账号创建，条件为 registration_enabled=true。
- 管理员与用户私有消息查询之间不要连线。

布局：管理员在左上、普通用户在左中、Adapter 在左下；系统边界内上方放认证和设置，中部放来源管理，下方放导入与查询。

## 4. 模块二用例图：AI 分析与信息聚合

参与者：
- 普通用户

用例：
- 选择模型
- 测试连接
- 单条分析
- 批量/窗口分析
- 判断消息是否有用
- 创建 InformationItem

关系：

## 5. 模块二局部 ER

实体：
- User
- Message
- AIAnalysis
- MessageInformation
- InformationItem

关系：
- User 1:N Message
- User 1:N InformationItem
- Message 1:0..N AIAnalysis
- Message 1:N MessageInformation
- InformationItem 1:N MessageInformation

Message 与 InformationItem 的概念联系是 M:N。MessageInformation 显示 user_id、message_id、information_id、relation_type；两组复合外键必须用粗线或注释突出“同一用户”。

案例标注：
- 初始通知 -> CREATE
- 补充附件 -> SUPPORT
- 修改内容 -> UPDATE
- 更正错误 -> CORRECTION

## 8. 完整用例图

参与者：
1. 普通用户
2. 系统管理员
3. 消息导入适配器
4. OpenAI-compatible AI 服务

普通用户用例：
- 注册（条件开放）、登录、退出、修改密码
- 管理 Channel
- 导入和查询 Message
- 选择模型、测试连接、单条/批量分析
- 浏览、修正、归档 InformationItem
- 查看来源、Category、Tag、Event 和统计

管理员用例：
- 管理员登录和修改密码
- 创建、启停用户、重置用户密码
- 控制注册开关
- 管理 Platform、Category

外部系统：
- Adapter 只连接导入消息。
- AI 服务连接模型列表、连接测试和消息分析。

绘图结论：管理员和普通用户功能边界分离，系统不存在“管理员查看全部消息”用例。

## 10. system_setting 绘图框

字段：
- setting_key PK
- value_text
- value_type
- is_sensitive
- description
- updated_at

示例行只用于图旁小表：

| key | type | sensitive |
|---|---|---:|
| registration_enabled | BOOLEAN | false |
| admin_password_hash | SECRET | true |
| admin_session_version | INTEGER | true |

讲解时强调：键名由程序白名单控制；普通设置接口不返回敏感 value_text；AI Key 不进入此表；业务数据不能塞入此表。

## 12. 常见答辩问题

### 为什么不用 User.role 表示管理员？

本项目只有一个系统管理入口，管理员不参与普通业务。独立管理 Cookie 和受控系统设置能保持普通 User 模型简单，也避免管理员误入用户私有数据。

### system_setting 会不会破坏数据库设计？

不会，因为它只保存少量、预先登记的系统开关和秘密，类型严格校验；Category、Tag、用户和消息等业务对象仍有独立关系表。

### 开放注册和管理员创建账号是否冲突？

不冲突。注册接口始终存在，但默认关闭；管理员可以按部署需要开启。关闭时只有管理员能创建账号。

### 数据隔离只靠查询条件吗？

不是。服务层从会话取得 user_id，Repository 强制过滤；MessageInformation 和 InformationTag 还用复合外键阻止跨用户关联。

### 为什么管理员看不到用户消息？

管理员职责是系统维护而不是内容审查。限制其访问能让隐私边界更清楚，也减少误操作和数据泄露风险。

## 13. 绘图自检

- 是否恰好 16 张核心表？
- 是否清楚区分 User 与 Sender？
- SystemSetting 是否独立且没有被画成业务万能表？
- Platform、Category 是否标为共享，Tag 是否标为私有？
- MessageInformation、InformationTag 是否标出同用户约束？
- Event 是否为 1:0..1？
- EventReminder 是否为 Event 的 1:0..1，且默认提醒/自定义/关闭/已读规则清楚？
- InformationItem 是否包含 version 乐观锁？
- 管理员用例中是否没有查看用户私有内容？
- 批量 AI 是否明确不跨用户和 Channel？
