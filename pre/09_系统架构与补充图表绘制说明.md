## 2. 系统边界图

### 2.1 中心系统框

标题：`UniBrief 校园多源消息智能聚合与信息管理系统`

框内放六个能力词，不放技术栈：

- 来源归一化
- 原始消息存储
- AI 结构化分析
- 有效信息聚合
- 事项与来源追溯
- 查询与统计

### 2.2 外部对象与箭头

| 位置 | 外部对象 | 流入系统 | 流出系统 |
|---|---|---|---|
| 左侧 | QQ/微信/钉钉外部采集工具 | 统一消息数据 | 导入结果 |
| 左下 | JSON/CSV 合成数据 | 演示消息 | 校验结果 |
| 右侧 | OpenAI-compatible AI 服务 | 模型列表、分析响应 | 测试/分析请求 |
| 上方 | 系统使用者 | 管理、导入、分析、查询操作 | 信息、事项、统计、错误提示 |

### 2.3 边界外注释

- 不逆向平台协议。
- 不包含账号与权限体系。
- 不包含自动回复、RAG、向量数据库和多 Agent。

这张图的结论是“系统从统一格式开始负责，原平台采集和协议不在课程设计范围内”。

## 3. 总体系统架构图

### 3.1 分层

从上到下画五层：

1. 表现层：React、TypeScript、Ant Design、TanStack Query、ECharts。
2. API 层：FastAPI REST API、Pydantic 请求/响应校验。
3. 业务层：platform、sender、ingestion、analysis、information、classification、event、statistics、search services。
4. 访问与集成层：Repository、Message Adapter、OpenAICompatibleProvider、AI 结果解析器。
5. 数据层：MySQL 8、Alembic migration、View、Trigger/自动维护、Stored Procedure 计划。

### 3.2 主要箭头

- Web UI -> REST API：HTTP/JSON。
- API -> Service：调用业务用例。
- Service -> Repository -> MySQL：事务性数据访问。
- Import UI/API -> Adapter -> Ingestion Service：统一消息输入。
- Analysis Service -> OpenAICompatibleProvider -> 外部 AI：事务外 HTTP 调用。
- Statistics Service -> View/统计查询 -> UI 图表。

### 3.3 图上的边界

- 用虚线框标出“本系统进程”和“外部 AI 服务”。
- 在 AI 箭头旁标注“可能超时/限流，失败可重试”。
- 在 MySQL 上方标注“原始证据 + 结构化信息 + 关系 + 状态 + 统计”。
- 不画 Redis、Kafka、Celery、向量数据库或微服务。

### 3.4 讲解重点

不要逐个念技术名，重点解释职责分离：Router 不写复杂业务，Service 控制事务，Repository 负责查询，Provider 隔离外部 AI 差异，Adapter 隔离消息来源格式。

## 4. 数据生命周期/证据链图

### 4.1 主链节点

从左到右画七个阶段，每阶段下方标表名：

1. 来源身份：platform、channel、sender。
2. 原始证据：message、message_attachment。
3. 分析记录：ai_analysis。
4. 有效信息：information_item。
5. 来源关联：message_information。
6. 组织与时间：category/tag/event 及关联表。
7. 消费：信息流、搜索、事项、统计、来源追溯。

### 4.2 两条回看箭头

- InformationItem -> MessageInformation -> Message：追溯原文。
- 统计页面 -> 基础表/View：统计口径可复核。

### 4.3 结论

> 原始数据不被 AI 结果覆盖，结构化信息也不脱离原始证据。

## 5. 数据流图 DFD

### 5.1 0 层 DFD

外部实体：

- E1 系统使用者
- E2 消息导入适配器
- E3 AI 服务

中心处理：

- P0 UniBrief 信息聚合系统

数据流：

- E1 -> P0：来源配置、导入指令、模型选择、查询条件、修正内容。
- P0 -> E1：导入结果、消息列表、信息详情、事项、统计、错误状态。
- E2 -> P0：统一消息与附件元数据。
- P0 -> E3：模型请求、连接测试、消息与候选信息。
- E3 -> P0：模型列表、测试结果、结构化分析响应或错误。

0 层 DFD 不画数据库表。

### 5.2 1 层 DFD

处理过程：

- P1 来源主数据管理
- P2 消息导入与去重
- P3 AI 分析与校验
- P4 有效信息聚合
- P5 查询、事项与统计

数据存储：

- D1 来源库：platform、channel、sender
- D2 原始消息库：message、message_attachment
- D3 分析记录库：ai_analysis
- D4 有效信息库：information_item、message_information
- D5 分类事项库：category、tag、两个关联表、event

主要流向：

1. E2 -> P2：消息批次。
2. P2 <-> P1 <-> D1：匹配或建立来源。
3. P2 -> D2：写新 Message 与附件。
4. E1 -> P3：模型与分析请求。
5. P3 <- D2：读取原文；P3 <- D4：读取候选信息。
6. P3 <-> E3：真实 AI 请求与响应。
7. P3 -> D3：保存分析记录。
8. P3 -> P4：已校验结构化结果。
9. P4 <-> D4/D5：创建、关联、更新信息及组织关系。
10. E1 <-> P5 <-> D1/D2/D4/D5：查询、追溯和统计。

注意：DFD 箭头名称写“消息批次”“结构化结果”等数据名，不写“调用”“处理”之类动作。

## 6. Message 状态转换图

### 6.1 状态

- PENDING：已导入，等待分析。
- PROCESSING：正在由指定模型分析。
- PROCESSED：有效消息已完成结果持久化。
- IGNORED：已分析但判断为无用。
- FAILED：AI 调用、输出校验或结果写入失败，可重试。

### 6.2 必画转换

| 起始状态 | 事件/条件 | 目标状态 |
|---|---|---|
| 新建 | Message 成功入库 | PENDING |
| PENDING | 用户发起分析 | PROCESSING |
| PROCESSING | 有效结果完整提交 | PROCESSED |
| PROCESSING | useful=false 且分析记录提交 | IGNORED |
| PROCESSING | AI/校验/数据库失败 | FAILED |
| FAILED | 用户更换模型或重试 | PROCESSING |

### 6.3 待定转换

项目支持多次 AIAnalysis，但 PROCESSED/IGNORED 是否允许再次进入 PROCESSING 尚需在实现前明确。绘图时可用虚线标为“可选重新分析”，并注明“待业务规则定稿”，不要把未确定行为画成已完成规则。

## 7. Event 状态转换图

### 7.1 状态

UPCOMING、ONGOING、COMPLETED、EXPIRED、CANCELLED。

### 7.2 建议转换

- 新建 Event -> UPCOMING 或 ONGOING，取决于 start_at。
- UPCOMING -> ONGOING：到达开始时间或人工更新。
- UPCOMING/ONGOING -> COMPLETED：事项完成。
- UPCOMING/ONGOING -> CANCELLED：通知取消。
- 未完成事项超过 deadline -> EXPIRED。

这些自动转换由应用任务还是查询时计算，现有设计尚未明确。第一次展示可以讲状态语义，不承诺后台自动调度。

## 8. AI 分析事务时序图

### 8.1 参与者

从左到右：User、React UI、Message API、Analysis Service、MySQL、OpenAI Provider。

### 8.2 正常时序

1. User -> UI：选择 model，点击分析。
2. UI -> API：提交 message_id + model。
3. API -> Analysis Service：校验后调用。
4. Analysis Service -> MySQL：更新 PROCESSING。
5. MySQL -> Analysis Service：commit。
6. Analysis Service -> MySQL：查询 Message 和近期 ACTIVE 候选。
7. Analysis Service -> OpenAI Provider：发送消息、候选和结构化输出要求。
8. OpenAI Provider -> Analysis Service：返回 JSON。
9. Analysis Service -> Analysis Service：解析并 Pydantic validate。
10. Analysis Service -> MySQL：begin 短事务。
11. Analysis Service -> MySQL：写 AIAnalysis、InformationItem/关联、Category/Tag、Event、最终状态。
12. MySQL -> Analysis Service：commit。
13. Analysis Service -> API -> UI：返回成功结果。

### 8.3 异常片段 alt

- AI 错误：跳过结果事务 -> 独立写 FAILED -> 返回分类错误。
- 校验失败：不写业务表 -> 独立写 FAILED -> 返回 INVALID_AI_OUTPUT。
- 结果事务失败：rollback 全部业务写入 -> 独立写 FAILED。

在时序图顶部用横条明确“AI HTTP 调用在数据库事务外”。

## 11. 统计图表设计

### 11.1 渠道消息量与有效率

- 图形：分组柱状图 + 有效率折线，或上下两个协调图。
- X 轴：Channel 名称。
- 左 Y 轴：总消息数、有效消息数。
- 右 Y 轴：有效率百分比。
- 数据来源：`v_channel_effectiveness` 或等价查询。
- 建议口径：有效消息是至少存在一条 MessageInformation 的 Message，按 `COUNT(DISTINCT message_id)` 去重；有效率为有效消息数除以总消息数，零总数安全返回 0。
- 讲解问题：哪些渠道信息价值高，哪些渠道噪声多？

### 11.2 Category 信息分布

- 图形：排序条形图优先；分类较少时可用环图。
- 维度：Category.name。
- 指标：InformationItem 数量。
- 数据来源：`v_category_statistics`。
- 讲解问题：近期校园信息主要集中在哪些类型？

### 11.3 Tag 热门度 Top N

- 图形：水平条形图。
- 维度：Tag.name。
- 指标：关联 InformationItem 次数。
- 数据来源：`v_tag_popularity` 或等价查询。
- 讲解问题：当前最活跃的具体主题是什么？

### 11.4 未来截止事项

- 图形：时间轴、按日期柱状图或紧凑事项列表。
- 维度：deadline 日期。
- 指标：未完成 Event 数量。
- 数据来源：`v_upcoming_events`。
- 讲解问题：未来 7 天有哪些时间压力？

设计阶段不要放看似真实但无法解释来源的漂亮数字。可以使用清楚标注“示意数据”的图，或只画图表结构占位。

## 12. 图表统一自检

- 架构图是否讲组件，流程图是否讲步骤，DFD 是否只讲数据流？
- 所有图的系统边界是否一致？
- 是否把真实 AI 服务画在系统外部？
- 是否始终把 MySQL 作为核心数据层？
- 状态图中的状态是否与 `docs/DATABASE.md` 一致？
- 是否没有画出尚未设计的定时任务、消息队列或权限系统？
- 图中任何新增字段或关系是否先回写数据库设计文档？
