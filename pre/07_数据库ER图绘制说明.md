# 数据库 E-R 图绘制说明

## 1. 图的定位

E-R 图用于数据库概念设计，回答三个问题：

1. 业务中有哪些实体？
2. 实体之间是什么联系？
3. 联系的基数和可选性是什么？

这张图不要展示所有字段类型、索引名和 API。完整字段放到数据库模型图。推荐使用 Crow's Foot 记法；若课程统一要求 Chen 记法，可将多对多关联实体改画为关系菱形。

## 2. 实体清单

概念层共有 10 类实体，关系模型通过 3 张关联表实现多对多。

| 编号 | 实体 | 中文含义 | 建议在 ER 图中保留的属性 |
|---|---|---|---|
| E1 | Platform | 消息平台 | id、name、type、status |
| E2 | Channel | 具体消息渠道 | id、external_id、name、channel_type |
| E3 | Sender | 外部消息发送者 | id、external_id、display_name、source_type、credibility |
| E4 | Message | 原始消息 | id、external_id、content、sent_at、process_status |
| E5 | MessageAttachment | 附件元数据 | id、file_type、file_name、file_url |
| E6 | AIAnalysis | 某条消息的一次 AI 分析 | id、model_name、useful、importance、confidence、summary、analyzed_at |
| E7 | InformationItem | 最终有效信息 | id、title、summary、importance、confidence、status |
| E8 | Category | 稳定粗粒度分类 | id、name、description |
| E9 | Tag | 动态细粒度标签 | id、name |
| E10 | Event | 有时间属性的事项 | id、start_at、deadline、event_status |

AIAnalysis 的 `raw_result` 可不放在概念图，以免误解为用 JSON 代替关系。讲解时说明它仅用于保留模型原始返回以便审计。

## 3. 联系与基数

| 编号 | 实体 A | 联系 | 实体 B | A 端基数 | B 端基数 | 业务解释 |
|---|---|---|---|---|---|---|
| R1 | Platform | 包含 | Channel | 1 | 0..N | 一个平台可有多个渠道，每个渠道只属于一个平台 |
| R2 | Platform | 标识 | Sender | 1 | 0..N | 发送者外部身份在平台范围内唯一 |
| R3 | Channel | 产生/承载 | Message | 1 | 0..N | 每条消息来自且只来自一个渠道 |
| R4 | Sender | 发送 | Message | 1 | 0..N | 每条消息由且只由一个 Sender 发送 |
| R5 | Message | 包含 | MessageAttachment | 1 | 0..N | 消息可以没有附件，也可有多个附件 |
| R6 | Message | 被分析 | AIAnalysis | 1 | 0..N | 未分析消息可以没有记录，同一消息可多次分析 |
| R7 | Message | 形成/支持/更新/纠正 | InformationItem | 0..N | 1..N（业务目标） | 双向多对多，联系本身有类型和创建时间 |
| R8 | InformationItem | 归属 | Category | 0..N | 0..N | 信息可属于多个稳定分类，分类可包含多条信息 |
| R9 | InformationItem | 标注 | Tag | 0..N | 0..N | 信息可有多个动态标签，标签可复用 |
| R10 | InformationItem | 转化为 | Event | 1 | 0..1 | 无时间属性时无 Event，有时最多一个 |

R7 的 InformationItem 端业务最小基数为 1，表示有效信息应有至少一条来源 Message。当前外键本身不能阻止孤立 InformationItem，因此需要由创建事务和测试保证；图旁可添加此说明，体现对“概念约束与数据库可执行约束”的区分。

## 4. 多对多联系的属性

### 4.1 Message - InformationItem

联系名称：`MessageInformation / 信息证据关系`

联系属性：

- relation_type：CREATE、SUPPORT、UPDATE、CORRECTION；
- created_at：关系建立时间。

这是需要重点讲解的多对多，因为联系本身包含业务语义，不能只用两端外键替代。

### 4.2 InformationItem - Category

联系名称：`InformationCategory / 信息分类关系`

当前无额外业务属性，只需要保证同一信息与同一分类不会重复关联。

### 4.3 InformationItem - Tag

联系名称：`InformationTag / 信息标签关系`

当前无额外业务属性，只需要保证同一信息与同一标签不会重复关联。

## 5. 推荐绘图布局

使用横向 16:9 画布，按数据生命周期从左到右布局。

### 5.1 左侧：来源域

- Platform 放最左上。
- Channel 放 Platform 右下方。
- Sender 放 Platform 正下方，与 Channel 上下对齐。
- Platform 分别连 Channel、Sender。

### 5.2 中左：原始消息域

- Message 放画布中心偏左，使用主强调色。
- Channel 和 Sender 分别连入 Message。
- MessageAttachment 放 Message 下方。
- AIAnalysis 放 Message 上方。

### 5.3 中右：有效信息域

- InformationItem 放画布中心偏右，使用第二主强调色。
- Message 与 InformationItem 之间留出较宽空间，放 MessageInformation 关联实体或联系菱形。
- relation_type 直接写在关联实体中。

### 5.4 右侧：组织与事项域

- Category 放 InformationItem 右上。
- Tag 放 InformationItem 右侧。
- Event 放 InformationItem 右下。
- Category、Tag 的多对多关联线尽量不交叉；Event 使用清晰的 1 : 0..1 标记。

## 6. 两种可选画法

### 6.1 课堂主图：简化概念 ER 图

- 只画 10 个实体。
- Message-InformationItem、InformationItem-Category、InformationItem-Tag 使用联系菱形。
- 每个实体只保留主键和 2 至 4 个代表属性。
- 优点：清晰，适合讲基数和业务语义。

### 6.2 报告图：带关联实体的 Crow's Foot ER 图

- 将 MessageInformation、InformationCategory、InformationTag 画成关联实体。
- 显示联合主键组成，但不必显示全部类型。
- 优点：概念模型到关系模型的转换过程更直观。

不要在同一页同时放两种记法。

## 7. 关键关系的口头解释

### 7.1 Platform - Channel - Message

平台只说明消息来自 QQ、微信还是钉钉；Channel 才表示具体群或频道。Message 的外部 ID 只需要在 Channel 内唯一，所以去重约束设计为 `(channel_id, external_id)`，而不是让 external_id 全局唯一。

### 7.2 Platform - Sender - Message

Sender 是外部聊天世界中的人或机器人，不是系统用户。一个人在不同平台可能有不同 external_id，因此 Sender 的唯一范围是 Platform。

### 7.3 Message - AIAnalysis

一次分析不是 Message 的固定属性。模型可能更换，失败后可能重试，也可能需要比较模型，因此单独建立 AIAnalysis，形成一对多。

### 7.4 Message - InformationItem

原始消息是证据，InformationItem 是整理后的业务事实。多条消息可以共同支持同一信息，一条消息也可能产生多个事项，因此是多对多。

### 7.5 InformationItem - Event

Event 不是所有信息都必须有的属性。只有识别到开始或截止时间时才创建，且一个信息项最多对应一个事项，因此为 1 : 0..1。

## 8. 概念模型转关系模型规则

| 概念联系 | 转换结果 |
|---|---|
| Platform 1:N Channel | 在 channel 放 `platform_id` 外键 |
| Platform 1:N Sender | 在 sender 放 `platform_id` 外键 |
| Channel 1:N Message | 在 message 放 `channel_id` 外键 |
| Sender 1:N Message | 在 message 放 `sender_id` 外键 |
| Message 1:N Attachment | 在 message_attachment 放 `message_id` 外键 |
| Message 1:N AIAnalysis | 在 ai_analysis 放 `message_id` 外键 |
| Message M:N InformationItem | 建 message_information，两个外键组成联合主键 |
| InformationItem M:N Category | 建 information_category，两个外键组成联合主键 |
| InformationItem M:N Tag | 建 information_tag，两个外键组成联合主键 |
| InformationItem 1:0..1 Event | 在 event 放 `information_id`，同时加 UNIQUE |

## 9. 绘图自检

- 是否明确标出每个关系的 1、0..1、0..N 或 1..N？
- 是否将 Sender 与系统 User 概念分开？
- 是否将 AIAnalysis 画成独立实体而不是 Message 的一组字段？
- 是否在 MessageInformation 上标出 relation_type？
- 是否将 Category 和 Tag 分别建模？
- 是否正确表达 Event 的可选一对一，而不是普通一对多？
- 是否避免在概念图中塞入所有字段、索引和 API？
