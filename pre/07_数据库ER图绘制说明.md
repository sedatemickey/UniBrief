# 数据库 E-R 图绘制说明（多用户版）

## 1. 图的定位

E-R 图用于概念设计，回答“有哪些实体、为什么存在、怎样联系、基数是什么”。概念图不要塞入全部字段类型、索引或 API；这些内容放在数据库模型图。

推荐使用 Crow's Foot。实体框只写英文名称，中文含义放在图旁图例。

## 2. 实体清单

概念层共有 13 类实体，关系模型另用 3 张关联表实现多对多，共 16 张表。新增的第 13 类实体是 EventReminder。

| 编号 | 实体 | 中文含义 | 主图代表属性 |
|---|---|---|---|
| E1 | User | 普通登录用户 | id、username、display_name、status |
| E2 | SystemSetting | 受控系统设置 | setting_key、value_type、is_sensitive |
| E3 | Platform | 全局消息平台 | id、name、type、status |
| E4 | Channel | 用户私有消息渠道 | id、user_id、external_id、name |
| E5 | Sender | 用户消息库中的外部发送者 | id、user_id、external_id、display_name |
| E6 | Message | 用户私有原始消息 | id、user_id、external_id、sent_at、process_status |
| E7 | MessageAttachment | 附件元数据 | id、file_type、file_name、file_url |
| E8 | AIAnalysis | 某条消息的一次 AI 分析 | id、model_name、useful、importance、confidence |
| E9 | InformationItem | 用户私有有效信息 | id、user_id、title、importance、status |
| E10 | Category | 全局稳定分类 | id、name、status |
| E11 | Tag | 用户私有细粒度标签 | id、user_id、name |
| E12 | Event | 有时间属性的事项 | id、start_at、deadline、event_status |

概念说明：

- User 是登录系统的人；Sender 是消息原文中的发送者，两者不能合并。
- SystemSetting 保存注册开关、管理员密码哈希和管理员会话版本等受控设置，不保存普通业务数据。
- Platform、Category 全局共享；Channel、Sender、Message、InformationItem、Tag 属于具体 User。
- AIAnalysis.raw_result 可从概念图省略，它只是审计副本。

## 3. 联系与基数

| 编号 | 实体 A | 联系 | 实体 B | A 端 | B 端 | 解释 |
|---|---|---|---|---|---|---|
| R1 | User | owns | Channel | 1 | 0..N | 每个 Channel 只属于一个 User |
| R2 | User | owns | Sender | 1 | 0..N | 同一外部发送者可在不同用户空间重复出现 |
| R3 | User | owns | Message | 1 | 0..N | 每条 Message 有明确用户归属 |
| R4 | User | owns | InformationItem | 1 | 0..N | 有效信息属于一个 User |
| R5 | User | owns | Tag | 1 | 0..N | Tag 名称只在用户内唯一 |
| R6 | Platform | contains | Channel | 1 | 0..N | Platform 是共享字典 |
| R7 | Platform | identifies | Sender | 1 | 0..N | Sender 外部身份按用户和平台区分 |
| R8 | Channel | carries | Message | 1 | 0..N | 每条消息来自一个 Channel |
| R9 | Sender | sends | Message | 1 | 0..N | 每条消息由一个 Sender 发送 |
| R10 | Message | contains | MessageAttachment | 1 | 0..N | 消息可以没有或有多个附件 |
| R11 | Message | is analyzed by | AIAnalysis | 1 | 0..N | 同一消息可以多次分析 |
| R12 | Message | supports | InformationItem | 0..N | 1..N（业务目标） | 同用户范围内 M:N |
| R13 | InformationItem | classified as | Category | 0..N | 0..N | 私有信息可关联共享分类 |
| R14 | InformationItem | tagged with | Tag | 0..N | 0..N | 两端必须属于同一 User |
| R15 | InformationItem | becomes | Event | 1 | 0..1 | 有时间属性时最多生成一个事项 |

SystemSetting 不与业务实体建立外键关系。可把它放在“系统配置域”独立框中，用注释说明 SettingService 和管理员认证读取它，不画虚假的 User-SystemSetting 联系。

## 4. 多对多联系

### 4.1 Message - InformationItem

关联实体：MessageInformation。

属性：user_id、message_id、information_id、relation_type、created_at。

relation_type：

- CREATE：该消息首次形成信息；
- SUPPORT：补充证据，不改核心事实；
- UPDATE：更新信息内容；
- CORRECTION：纠正原通知。

概念上是 M:N；物理模型通过两组带 user_id 的复合外键保证两端属于同一 User。

### 4.2 InformationItem - Category

关联实体：InformationCategory。Category 全局共享，因此关联表不需要 user_id；InformationItem 本身已经有用户归属。

### 4.3 InformationItem - Tag

关联实体：InformationTag，包含 user_id、information_id、tag_id。复合外键保证私有 InformationItem 与私有 Tag 属于同一 User。

## 5. 三个模块的局部 ER 图

### 5.1 模块一：用户、来源与原始归档

实体：User、SystemSetting、Platform、Channel、Sender、Message、MessageAttachment。

主线：

- User 1:N Channel/Sender/Message；
- Platform 1:N Channel/Sender；
- Channel、Sender 分别 1:N Message；
- Message 1:0..N MessageAttachment；
- SystemSetting 独立。

讲解重点：User 决定私有空间；Platform 共享；Sender 不是 User；原文先保存。

### 5.2 模块二：分析与有效信息聚合

实体：User、Message、AIAnalysis、MessageInformation、InformationItem。

主线：

- User 1:N Message/InformationItem；
- Message 1:0..N AIAnalysis；
- Message M:N InformationItem，经 MessageInformation。

讲解重点：多条通知可以共同支持同一信息；所有候选和关联只在同一用户范围内。

### 5.3 模块三：组织、事项与统计

实体：User、InformationItem、Category、InformationCategory、Tag、InformationTag、Event。

主线：

- User 1:N InformationItem/Tag；
- InformationItem M:N Category；
- InformationItem M:N Tag；
- InformationItem 1:0..1 Event。

讲解重点：Category 共享、Tag 私有、Event 可选且唯一。

## 6. 完整 ER 图布局

横向 16:9，从左到右按数据生命周期布局：

- 左上“账号与配置域”：User、SystemSetting；两者不连外键。
- 左侧“来源域”：Platform 上方，Channel 与 Sender 下方；User 连向 Channel、Sender。
- 中左“消息域”：Message 为第一核心实体；Attachment 在下，AIAnalysis 在上。
- 中间：MessageInformation。
- 中右“信息域”：InformationItem 为第二核心实体；User 连向它。
- 右侧“组织事项域”：Category/InformationCategory 在上，Tag/InformationTag 在中，Event 在下。

配色：

- 全局实体 Platform、Category、SystemSetting：一种浅色；
- 用户私有实体：另一种颜色；
- Message、InformationItem：两个强调色；
- 三张关联表：统一中性色。

不要把所有 User 连线画成穿越全图的斜线，可使用对齐后的折线或重复一个带“同一 User”说明的只读锚点。

## 7. 关键关系的口头解释

### User 与 Sender

User 是登录系统、拥有数据空间的人。Sender 是 QQ/微信/钉钉消息中的教师、学生或机器人。一个 User 会保存许多 Sender，不能用 Sender 代替账号。

### User 与私有数据

User 直接拥有 Channel、Sender、Message、InformationItem 和 Tag。附件、分析记录和 Event 通过父实体继承归属。服务层过滤与数据库复合外键共同保证隔离。

### Platform/Category 共享，Tag 私有

平台名称和课程、竞赛等大类需要全站统一；具体标签来自个人消息内容，按 User 独立，避免暴露或混淆其他用户主题。

### Message 与 InformationItem

Message 保存证据，InformationItem 保存整理结果。作业通知、附件补充和截止时间更正可以共同指向同一信息，因此不是一对一。

### InformationItem 与 Event

只有带时间的信息才有 Event；event.information_id 同时为外键和唯一键，从数据库保证一个信息最多一个事项。

### SystemSetting

SystemSetting 是受控键值表。键名、类型和敏感性由代码白名单决定；SECRET 不返回前端，AI Key 仍只在环境变量中。

## 8. 概念模型转关系模型

| 概念联系 | 关系模型实现 |
|---|---|
| User 1:N Channel/Sender/Message/InformationItem/Tag | 在私有实体放 user_id FK |
| Platform 1:N Channel/Sender | 在 Channel、Sender 放 platform_id |
| Channel/Sender 1:N Message | Message 使用同 user_id 的复合外键 |
| Message 1:N Attachment/AIAnalysis | 子表放 message_id |
| Message M:N InformationItem | 建 MessageInformation，并加入同用户复合外键 |
| InformationItem M:N Category | 建 InformationCategory |
| InformationItem M:N Tag | 建 InformationTag，并加入同用户复合外键 |
| InformationItem 1:0..1 Event | Event 放 information_id FK + UNIQUE |

概念图中的“有效信息至少有一条来源 Message”无法只靠现有外键阻止孤立记录，需要创建事务和测试保证。

## 9. 绘图自检

- 是否为 13 类实体和 3 张关联表，共 16 张表？
- 是否画出 Event 1 : 0..1 EventReminder？
- 是否明确区分 User 与 Sender？
- SystemSetting 是否独立且没有虚假业务联系？
- Platform、Category 是否标为共享，Tag 是否标为私有？
- 是否画出 User 对五类私有实体的归属？
- Message-InformationItem、InformationItem-Tag 是否注明同用户约束？
- 是否正确表达 3 个 M:N 和 1 个 1:0..1？
- 是否避免在概念图中塞入全部字段、索引、Cookie 或 API？
