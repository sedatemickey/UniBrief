# 答辩准备与讲解建议

## 1. 讲解总原则

每个设计点都按“业务问题 -> 数据库设计 -> 如何验证”回答。

例如不要只说“建了唯一索引”，而要说：

> 同一消息可能被重复导入，所以 Message 以 channel_id 和 external_id 建复合唯一约束；应用层先查询，数据库约束处理并发兜底；后续用同一批数据导入两次验证 Message 数量不增加。

## 2. 最应强调的五点

1. Message 原文与 InformationItem 有效信息分离，保证来源追溯。
2. Message-InformationItem 使用多对多，支持补充、更新与纠正。
3. Event 的外键加唯一约束直接表达 1 : 0..1。
4. AI 调用在事务外，结果在短事务内原子持久化，失败不丢原文。
5. 统计、索引、约束和高级数据库对象都由具体业务查询驱动。

## 3. 常见答辩问题与建议回答

### Q1：为什么这个题目适合数据库课程设计，而不是一个 AI 套壳？

系统有 16 张核心表，包含 1:N、M:N 和 1:0..1，多组真实外键、复合外键、联合主键和唯一约束。AI 只负责把自然语言转成候选结构，最终的数据保存、聚合、追溯、状态、事项和统计都由关系数据库承担。即使更换 AI 供应商，数据库模型和核心业务仍然成立。

### Q2：为什么 Message 和 InformationItem 不合成一张表？

Message 是不可轻易修改的原始证据，InformationItem 是会被补充、更新、纠正和归档的结构化信息。二者生命周期不同，而且多条消息可以支持同一信息，一条消息也可能包含多个信息项，因此必须分表并通过多对多关联。

### Q3：为什么是一对多的 AIAnalysis？

同一 Message 可能因为超时重试、模型更换或模型效果比较被多次分析。把分析记录独立出来可以保存实际模型和分析时间，避免 Message 只能保留最后一次结果。

### Q4：为什么同时需要 Category 和 Tag？

Category 是稳定的粗粒度导航和统计维度，例如课程、竞赛、活动；Tag 是动态细粒度主题，例如数据库系统、报名、CCPC。二者用途不同，分别建表和建立多对多关系能同时支持稳定统计与灵活检索。

### Q5：为什么 Event 不是 InformationItem 中几个可空时间字段？

只有部分信息有事项属性。Event 有独立状态和时间查询需求，单独建表能避免在所有信息行上堆积无意义字段，也能独立建立 deadline 索引。`information_id` 外键加唯一键保证每条信息最多一个 Event。

### Q6：怎样防止重复导入？

先归一化 Platform、Channel 和 Sender，再以 `(channel_id, external_id)` 识别 Message。应用层查询改善反馈，数据库唯一约束处理并发兜底。同一批数据导入两次时，第二次只增加 duplicate 计数，不增加 Message。

### Q7：为什么 external_id 不是全局唯一？

外部 ID 的命名空间由平台或渠道决定。不同平台可能出现相同 sender external_id，不同渠道也可能出现相同 message external_id，因此唯一范围分别设计为 Platform 内或 Channel 内，更符合真实业务。

### Q8：AI 判断错了怎么办？

原始 Message 永久保留，信息详情可追溯所有来源；InformationItem 允许人工修正标题、摘要、重要度和状态；补充与纠正消息也通过关系类型保留。AI 输出还必须先经过模式校验，不能直接写业务表。

### Q9：AI 服务不可用怎么办？

Message 已经先入库。认证、模型不存在、限流、超时、网络和非法输出分别分类，消息进入 FAILED 并允许更换模型重试。失败不会产生半成品 InformationItem，也不会用 Mock AI 伪造成功结果。

### Q10：为什么 AI 请求不能放在数据库事务里？

网络调用时间不可控，放在事务中会长时间占用连接和锁。设计先提交 PROCESSING 状态，在事务外调用 AI，成功后再用短事务原子写入全部结果，兼顾可观察性和数据一致性。

### Q11：如果写 AIAnalysis 成功，但写 Event 失败怎么办？

AIAnalysis、InformationItem、关联表、Category/Tag、Event 和最终 Message 状态属于同一次结果持久化短事务。Event 写入失败时整体 rollback，不留下部分成功；之后独立把 Message 标记为 FAILED。

### Q12：如何保证一个 InformationItem 只有一个 Event？

`event.information_id` 不只是外键，还建立 UNIQUE。外键保证 Event 指向真实信息，唯一键保证同一信息不能插入第二个 Event，业务规则由数据库直接执行。

### Q13：数据库满足第几范式？

设计目标为第三范式。字段原子化满足 1NF；关联表中的关系属性依赖完整联合主键，满足 2NF；平台、渠道、发送者、分类、标签等独立建表，非主属性不通过其他非主属性传递依赖，减少更新异常，满足 3NF。

### Q14：既然强调关系模型，为什么还有 JSON 字段？

`ai_analysis.raw_result` 只保存供应商原始响应作为审计副本，不参与核心关系查询。Category、Tag、Event 和 MessageInformation 等业务结构都已正规建表，没有用 JSON 替代关系。

### Q15：为什么这些索引的字段顺序这样设计？

组合索引先放常用等值条件，再放范围或排序字段。例如消息按某渠道和时间范围查询，所以是 `(channel_id, sent_at)`；事项先按状态筛选再按 deadline 查询，所以是 `(event_status, deadline)`。实现后会用 EXPLAIN 验证。

### Q16：三个统计具体是什么？

固定三项是各 Channel 的总消息数、有效消息数和有效率，各 Category 的 InformationItem 数量，以及 Tag 热门度 Top N。附加统计是未来 7 天截止 Event。它们分别体现基础表聚合、多对多关联聚合和时间范围查询。

### Q17：为什么要有 User 表，但管理员不使用 User.role？

系统按多用户私有数据空间实现，User 表用于普通用户登录和数据归属，Sender 是外部消息发送者，两者不能混淆。管理员不作为 User 角色，而是使用独立 Cookie 和 system_setting 中受控的密码哈希，只管理账号、注册开关和全局字典，不能读取用户私有消息。

### Q18：消息怎么从 QQ、微信、钉钉获取？

本系统不逆向私有协议。基础路径使用 JSON、CSV 和合成数据；QQ 可选接入 NapCatQQ，通过独立 OneBot 11 Adapter/桥接进程把消息事件转换成同一导入格式。UniBrief 不管理 QQ 登录、不发送消息、不自动回复，核心数据库模型不变。

### Q19：为什么不用向量数据库做信息去重？

课程 MVP 规模和目标不需要复杂向量检索。先从近期 ACTIVE 信息中用标题关键词和简单相似规则筛选有限候选，再让真实 AI 在候选内选择 create、link 或 update，设计更容易解释、测试和演示。

### Q20：演示数据如何满足课程数量要求？

计划生成不少于 1,000 条合成 Message、不少于 30 条 InformationItem 和不少于 200 条关联记录。数据包含闲聊、重复导入、补充、纠正、带截止时间和 AI 失败场景，并提供固定 reset/seed/verify 流程。

### Q21：Trigger 和 Stored Procedure 准备做什么？

计划用数据库 Trigger 更新 `information_item.updated_at`，并必须实现 `sp_channel_statistics(p_user_id, p_start, p_end)` 返回当前用户在时间区间内各渠道消息量、有效消息量和有效率。两者都通过 Alembic migration 创建并测试。

### Q22：系统现在做到什么程度？

截至 2026-09-01，Phase 0–5 已完成并进入 Phase 6 收尾：16 表、迁移、认证、导入、附件、真实 OpenAI-compatible Provider、统计高级对象、周期任务、完整 Web UI 和 1000+ 条合成演示数据均已实现并有自动化测试。必须同时如实说明：真实 AI 成功联调仍依赖用户提供 Key/model，NapCat 真实联调依赖第三方框架搭建，clean clone 最终验证也要保留记录。

## 4. 当前设计的主动说明

下列口径已经冻结：AIAnalysis 同时记录成功/失败尝试；每个 item 独立 action；InformationItem 使用 version 乐观锁；有效消息按至少关联一个 InformationItem 的 distinct Message；Event/Reminder 和 20 条/5 分钟窗口由单实例周期任务维护；所有时间按 UTC 入库、上海时区显示。实施后仍应以真实 migration、API 和测试结果为准。

## 6. 现场讲图方法

### 用例图

先指出三类参与者，再顺着“导入、分析、查询”三组用例讲，不逐个念所有椭圆。

### 流程图

用手势沿主线移动，只在“是否重复、AI 是否成功、是否有用、是否有时间属性”四个菱形停顿。

### ER 图

先找两个中心实体 Message 和 InformationItem，再向左讲来源、向右讲分类标签事项，最后解释中间的多对多。

### 模型图

不要逐字段朗读。先分五个数据域，再只圈出四类关键标记：外键、复合唯一键、联合主键、Event 唯一外键。

### 时序图

只强调三段：状态先提交、AI 在事务外、结果短事务原子提交。

## 8. 最后 30 秒结论稿

> UniBrief 的核心不是生成一段 AI 摘要，而是把校园消息转化为可靠的数据关系。原始 Message 作为证据保留，InformationItem 聚合有效信息，多对多关系记录补充和纠正，Category、Tag、Event 支持组织、提醒与统计，唯一约束、索引和事务保证数据正确。AI 负责理解自然语言，数据库负责让结果可管理、可追溯、可验证。
