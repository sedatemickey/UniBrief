# 业务流程图绘制说明（多用户版）

正文推荐绘制“登录用户导入消息到查看信息”的完整泳道图。账号管理、导入去重、AI 窗口、信息聚合和失败重试可作为局部图或备份页。

## 1. 图 A：代表性完整业务流程

### 1.1 泳道

使用五条泳道：

1. 普通用户 / React UI
2. FastAPI 与业务 Service
3. MySQL
4. OpenAI-compatible AI 服务
5. 系统管理员（只在账号准备阶段出现，可缩成图左上角旁路）

消息导入 Adapter 放在导入节点旁，不必单独占泳道。

### 1.2 节点顺序

| 序号 | 泳道 | 节点 | 后续 |
|---:|---|---|---|
| 1 | 管理员 | 创建普通用户，或开启注册开关 | 2 |
| 2 | 数据库 | 写 User 或更新 SystemSetting | 3 |
| 3 | 普通用户 | 登录 | 4 |
| 4 | Service | 校验密码和账号状态，签发普通用户 Cookie | 5 |
| 5 | 普通用户 | 选择 JSON/CSV 文件 | 6 |
| 6 | Service | 从会话取得 user_id，校验输入格式 | 7 |
| 7 | Service | 匹配全局 Platform 和当前用户 Channel/Sender | 8 |
| 8 | 数据库 | 判断用户范围内 Message 是否重复 | 重复到 9，新消息到 10 |
| 9 | Service | 记为 duplicate，不新增 Message | 11 |
| 10 | 数据库 | 写 Message=PENDING 和附件，提交 | 11 |
| 11 | UI | 返回 inserted、duplicate、failed 数量 | 12 |
| 12 | 用户/系统 | 手动发起分析，或等待窗口触发 | 13 |
| 13 | Service | 确认批次属于同一 user_id 和 Channel | 14 |
| 14 | 数据库 | Message -> PROCESSING，提交 | 15 |
| 15 | Service/数据库 | 查询同一用户近期 ACTIVE InformationItem 候选 | 16 |
| 16 | AI 服务 | 分析消息并返回结构化 JSON | 17 |
| 17 | Service | 调用成功且 Pydantic 校验通过？ | 否到 18，是到 19 |
| 18 | 数据库 | Message -> FAILED，记录错误，可重试 | 30 |
| 19 | Service | useful 是否为 true？ | 否到 20，是到 21 |
| 20 | 数据库 | 短事务写 AIAnalysis；Message -> IGNORED | 30 |
| 21 | Service | 动作是 create / link / update？ | 22 |
| 22 | 数据库 | 创建、关联或更新同用户 InformationItem | 23 |
| 23 | 数据库 | 写同用户 MessageInformation 与 relation_type | 24 |
| 24 | 数据库 | 关联共享 Category、归一化私有 Tag | 25 |
| 25 | Service | 是否有时间属性？ | 是到 26，否到 27 |
| 26 | 数据库 | 创建或更新唯一 Event；有 Deadline 时原子维护 EventReminder | 27 |
| 27 | 数据库 | Message -> PROCESSED，提交完整短事务 | 28 |
| 28 | UI | 刷新当前用户信息流、事项和统计 | 29 |
| 29 | 用户 | 查看详情并追溯自己的原始 Message | 30 |
| 30 | 用户 | 完成信息处理闭环 | 结束 |

### 1.3 事务边界

- 节点 10：原始 Message 入库事务，独立于 AI。
- 节点 14：PROCESSING 更新立即提交。
- 节点 16：外部 HTTP 调用，明确标注“数据库事务外”。
- 节点 20 或 22 至 27：结果持久化短事务。
- 结果事务任一步失败：整体 rollback，再用独立事务写 FAILED。

图上结论：

> 身份先确定归属，原文先入库；AI 在事务外调用，结果在同用户短事务中原子提交。

## 2. 图 B：账号、注册开关与管理员流程

### 2.1 管理员初始化

1. 运维人员运行交互式初始化脚本。
2. 脚本读取管理员密码，不回显、不写日志。
3. 使用 Argon2id 生成哈希。
4. upsert SystemSetting.admin_password_hash。
5. 初始化或递增 admin_session_version。
6. 管理员使用独立登录页登录。

### 2.2 用户创建的两条路径

路径一，默认：

1. registration_enabled=false。
2. 管理员创建用户名、显示名和初始密码。
3. 系统校验 username 唯一并写 User。
4. 用户登录后可自行修改密码。

路径二，管理员开启注册：

1. 管理员把 registration_enabled 改为 true。
2. 登录页显示注册入口。
3. 用户提交用户名、显示名和密码。
4. 服务端再次读取注册开关，不能只相信前端。
5. 注册成功创建 ACTIVE User。

### 2.3 停用与重置

- 停用用户：User.status -> DISABLED，session_version + 1，保留业务数据。
- 重置密码：写新哈希，session_version + 1。
- 管理员改密：更新 admin_password_hash，admin_session_version + 1。
- 管理员 Cookie 与普通用户 Cookie 必须分开。

## 3. 图 C：消息导入与用户级幂等

节点：

1. 普通用户会话校验成功。
2. 从会话取得 user_id，不接受文件或请求体提供的 user_id。
3. 校验平台、渠道 external_id、发送者 external_id、消息 external_id、正文和发送时间。
4. 查找 ACTIVE 全局 Platform。
5. 按 (user_id, platform_id, channel.external_id) 查找或创建 Channel。
6. 按 (user_id, platform_id, sender.external_id) 查找或创建 Sender。
7. 按 (user_id, channel_id, message.external_id) 查询 Message。
8. 已存在：记 duplicate。
9. 不存在：写 Message=PENDING 和零到多个 MessageAttachment。
10. 并发唯一键冲突：按 duplicate 处理。
11. 返回 inserted、duplicate、failed。

绘图重点：

- 应用层预查和数据库唯一约束都要画出。
- Channel、Sender、Message 的唯一范围都包含用户归属。
- 甲用户导入过的外部消息不妨碍乙用户在自己的空间导入。

## 4. 图 D：AI 双阈值窗口

### 4.1 分组键

等待队列按 (user_id, channel_id) 分组，禁止跨用户或跨 Channel 合批。

### 4.2 触发逻辑

1. 新 Message 进入 PENDING。
2. 检查该分组等待条数。
3. 条数达到 20？是则触发。
4. 否则检查最早消息等待时间。
5. 等待达到 5 分钟？是则触发。
6. 两者都未达到：继续等待。
7. 用户点击“立即分析”：直接触发所选合法消息。
8. 触发前再次验证所有 Message 属于同一用户和 Channel。
9. 一次调用 AI，返回结果仍逐条对应 Message 保存。

图旁注明：20 条和 5 分钟是可配置初始值，当前不新增批次实体表。

## 5. 图 E：InformationItem 聚合决策

输入：

- 当前用户的 Message；
- 已校验 AI 结果；
- 当前用户近期 ACTIVE InformationItem 候选。

节点：

1. 提取标题关键词和主题。
2. 只从同一 user_id 的近期信息形成有限候选集。
3. AI 选择 create、link 或 update。
4. create：新建同用户 InformationItem，relation_type=CREATE。
5. link：只增加 MessageInformation，通常为 SUPPORT。
6. update：更新信息并增加 UPDATE 关系。
7. 纠正原通知：使用 CORRECTION。
8. 关联全局 Category。
9. 按 (user_id, name) 归一化私有 Tag。
10. 有时间属性则创建或更新唯一 Event；有 Deadline 时在同一短事务中创建或维护 EventReminder。
11. 统一提交。

案例：

- M1“数据库作业周五前提交” -> 创建 I1。
- M2“补充模板附件” -> SUPPORT I1。
- M3“截止改为下周一 18:00” -> CORRECTION I1 并更新 Event。

三条原文保留，但该用户信息流只展示一个持续演化的 I1。其他用户不会成为候选来源。

## 6. 图 F：失败、越权与重试

### 6.1 AI 失败

错误类型：AUTH_ERROR、MODEL_NOT_FOUND、RATE_LIMITED、TIMEOUT、NETWORK_ERROR、PROVIDER_ERROR、INVALID_AI_OUTPUT。

统一路径：

1. Message -> FAILED。
2. 原文和附件保持不变。
3. 不留下半成品 InformationItem。
4. 用户修复配置、换模型或稍后重试。
5. 不存在“返回模拟分析结果”分支。

### 6.2 越权访问

1. 用户 A 请求一个不属于自己的 Message/InformationItem/Tag ID。
2. Service 使用会话 user_id 查询。
3. 查询不到时统一返回 404，不暴露资源是否属于用户 B。
4. 即使业务代码漏检，MessageInformation 和 InformationTag 的复合外键仍拒绝跨用户写入。

### 6.3 管理员边界

- 管理员会话只能访问 /admin 范围。
- 管理员可管理 User、SystemSetting 非敏感设置、Platform、Category。
- 管理员端不提供用户 Message、InformationItem、Tag、Event 或统计查询。

## 7. 第二次课堂演示流程预告

1. 管理员创建两个普通用户，或临时打开注册。
2. 用户 A 登录并导入合成消息。
3. 用户 B 登录，验证看不到用户 A 数据。
4. 用户 A 重复导入同一批消息，展示幂等。
5. 加载或手工输入真实模型并测试连接。
6. 分析消息，展示闲聊过滤、聚合、Category、私有 Tag 和 Event。
7. 从 InformationItem 追溯原文。
8. 展示三类当前用户统计。
9. 演示 AI 失败重试或停用用户使旧会话失效。

登录不是代表性主流程，演示重点仍是“导入 -> 分析 -> 聚合 -> 追溯 -> 统计”。

## 8. 绘图规范与自检

- 泳道是否明确普通用户、Service、数据库、AI 和管理员的责任？
- 每个普通业务节点是否隐含或明确使用当前 user_id？
- 导入去重是否使用 (user_id, channel_id, external_id)？
- AI 窗口是否按同一用户、同一 Channel 分组？
- 候选信息和私有 Tag 是否限定当前用户？
- AI HTTP 是否在数据库事务外？
- 结果失败是否整体回滚且原文保留？
- 管理员是否无法进入用户私有内容？
- 是否没有 Mock AI、跨用户共享或未设计的消息队列？
