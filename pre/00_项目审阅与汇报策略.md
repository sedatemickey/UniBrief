# 项目审阅与汇报策略

## 1. 一句话定位

UniBrief 是一个单用户的校园多源消息智能聚合与信息管理系统：它把来自 QQ、微信、钉钉等渠道的消息统一导入，以真实 OpenAI-compatible AI 完成有效性判断、摘要、分类和时间识别，再由关系数据库保存可检索、可追溯、可统计的结构化信息。

课堂上建议反复强调：**AI 负责理解消息，数据库负责保存事实、关系、约束和证据链，数据库才是系统主角。**

## 2. 现有设计的完整链路

现有设计已经形成一条清晰的数据生命周期：

1. JSON、CSV 或模拟 Adapter 提供统一格式消息。
2. Platform、Channel、Sender 先完成来源归一化。
3. Message 和 MessageAttachment 保存原始证据，唯一约束保证重复导入不会产生重复消息。
4. 用户选择真实 AI 模型，系统将 Message 标记为 PROCESSING 后提交短事务。
5. OpenAI-compatible Provider 返回结构化结果，Pydantic 严格校验。
6. AIAnalysis 保存一次分析记录。
7. 无效消息进入 IGNORED；有效消息创建、关联或更新 InformationItem。
8. MessageInformation 保存原始消息与有效信息的多对多证据关系。
9. Category 和 Tag 分别表达稳定大类与动态主题，并通过关联表与 InformationItem 建立多对多关系。
10. 有明确时间属性的信息生成至多一个 Event。
11. Web 页面支持查询、筛选、追溯和至少三类统计。

这条链路应成为整场汇报的主线。每讲一个表或模块，都回答它在这条链路中解决什么问题。

## 3. 示例 PPT 的借鉴与改进

示例 PPT 共 15 页，顺序为：

- 封面、目录；
- 需求分析：背景、系统设想、功能分类、用例图、业务流程图；
- 系统框架：前后端与技术栈；
- 数据库设计：ER 图、数据库模型图、安全性、高效性、可靠性；
- 结束页。

适合借鉴的部分：

- 三段式叙事清楚，符合第一次展示的评分结构；
- 用例图和流程图放在需求之后，先讲“为什么、做什么”，再讲“如何设计”；
- ER 图和模型图分开，能区分概念设计与逻辑/物理设计；
- 最后单独说明安全、效率和可靠性，覆盖非功能需求。

需要改进的部分：

- 不使用大段背景文字，单页最多保留 3 至 5 个观点；
- 技术栈只讲选择理由，不罗列工具功能；
- 数据库部分占至少一半有效讲解时间，对应课程 15 分数据库设计；
- 约束、索引、事务、视图、触发器、存储过程必须和具体业务问题对应；
- 所有图都要能沿“原始消息 -> 有效信息 -> 事项/统计 -> 来源追溯”主线解释。

## 4. 评分导向的时间与内容配比

第一次展示评分为功能需求 10 分、性能及其他需求 5 分、数据库设计 15 分。10 分钟汇报建议按下表分配：

| 部分 | 建议时间 | 对应重点 |
|---|---:|---|
| 封面与目录 | 0:20 | 一句话定位、汇报结构 |
| 功能需求与用例 | 2:30 | 问题、边界、参与者、功能、代表性流程 |
| 性能及其他需求 | 0:35 | 集中讲性能、可靠性、安全、易用性；第 16 页再结合事务补充 45 秒 |
| 系统架构过渡 | 0:35 | 只解释数据如何进入数据库，不展开工具功能 |
| 数据库设计 | 5:35 | 数据生命周期、ER、10 类实体、各种关系、13 表模型、约束、索引、事务和高级对象 |
| 总结 | 0:25 | 数据库价值和后续实现目标 |

上表总时长为 10 分钟。第 16 页同时支撑“性能及其他需求”和“数据库设计”两个评分点，但时间只计入数据库设计行，避免重复计算。

## 5. 最有辨识度的设计亮点

### 5.1 原始证据与结构化信息分离

Message 保存不可轻易删除的原始消息，InformationItem 保存系统整理后的有效信息。这样既能提高浏览效率，又能从每条摘要追溯原文，避免 AI 结果成为不可验证的“黑盒结论”。

### 5.2 多对多信息聚合

Message 与 InformationItem 不是简单一对一。一条消息可能包含多个事项，多条提醒也可能共同支持同一事项，因此通过 MessageInformation 建模，并用 CREATE、SUPPORT、UPDATE、CORRECTION 表达消息的业务作用。

### 5.3 分类与标签分工

Category 是稳定的粗粒度大类，适合导航和统计；Tag 是动态的细粒度主题，适合搜索和热点分析。二者分别建表并与 InformationItem 建立多对多关系，避免把标签塞进逗号字符串。

### 5.4 Event 的 1 : 0..1 约束

不是所有有效信息都有时间属性，因此 InformationItem 可以没有 Event；有时间属性时至多对应一个 Event。`event.information_id` 同时是外键和唯一键，数据库直接保证这一业务规则。

### 5.5 AI 失败不破坏原始数据

AI 网络调用不放在长事务中。Message 先独立入库并提交，AI 失败时只改变处理状态，不丢失原文，也不留下半成品 InformationItem，用户可更换模型后重试。

## 6. 当前设计需在实现前定稿的问题

这些问题不影响第一次展示的主体结构，但答辩时不要把它们说成已经完全解决。

| 编号 | 当前问题 | 建议定稿方向 | 汇报时的稳妥表述 |
|---|---|---|---|
| R1 | `channel`、`sender` 没有 status 字段，但删除策略写了“改状态” | 增加状态字段，或明确只禁止删除而不做停用 | “来源主数据采用受控删除；具体停用字段将在物理设计阶段定稿” |
| R2 | AI 错误要求分类并清晰记录，但当前 `ai_analysis` 只适合成功结果 | 决定在 `ai_analysis` 增加 status/error_type/error_message，或另建分析尝试表 | “设计会持久化可重试状态与错误分类，字段方案在实现前冻结” |
| R3 | AI 输出顶层只有一组 action/target，但 `items` 可包含多个信息项 | 将 action、target、relation_type 下沉到每个 item，或限制单次动作语义 | “数据库支持一条消息拆分多个信息项，AI 输出粒度会与该能力对齐” |
| R4 | AGENTS 的去重章节残留 MockAIProvider 描述，与运行时禁止 Mock 的总原则冲突 | 以 `AI_INTEGRATION.md` 和 D004 为准，删除或改写过时表述 | “产品和演示只使用真实 OpenAI-compatible Provider” |
| R5 | Trigger 和 Stored Procedure 目前还是推荐方案，尚未落地 | Trigger 固定为维护 `information_item.updated_at`；存储过程固定为区间渠道统计，或在决策日志说明省略 | “数据库高级对象为计划设计，实施后以迁移文件为准” |
| R6 | “渠道有效消息数”的统计口径尚未在源设计中完全冻结 | 建议定义为至少存在一条 MessageInformation 的去重 Message 数，并使用 `COUNT(DISTINCT message_id)` | “统计口径以是否形成有效信息关系为准，避免多关联重复计数” |

## 7. 汇报中必须区分的概念

| 容易混淆 | 正确区分 |
|---|---|
| 消息源与本系统用户 | Sender 是外部消息发送者；系统是单用户，不设计 User 表 |
| 模拟消息与模拟 AI | 允许使用合成 JSON/CSV 消息；运行时不允许用 Mock AI 替代真实 API |
| AIAnalysis 与 InformationItem | 前者是对某条消息的一次模型分析记录；后者是最终可浏览、可聚合的有效信息 |
| Category 与 Tag | Category 稳定、粗粒度；Tag 动态、细粒度 |
| ER 图与数据库模型图 | ER 图讲业务实体和联系；模型图讲表、字段、键、约束和索引 |
| 架构图与业务流程图 | 架构图讲组件及依赖；流程图讲业务步骤、判断和异常分支 |
| 当前设计与已实现功能 | 当前只完成设计资料，系统实现尚未开始 |

## 8. 建议的核心结论

结尾不要只说“我们使用了 AI”。建议使用以下结论：

> 本系统的关键不是把聊天消息交给 AI，而是建立一套以关系数据库为核心的信息治理链路：原始消息完整保留，有效信息结构化聚合，分类、标签和事项形成可查询关系，任何结论都能追溯来源，重复导入、状态流转和一对多、多对多规则由约束与事务共同保证。
