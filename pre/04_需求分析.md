# 需求分析

> **已废止（Superseded）**：本文对应早期单用户需求基线。当前需求以 `AGENTS.md`、`docs/COURSE_REQUIREMENTS.md`、`docs/ARCHITECTURE.md`、`docs/DATABASE.md`、`docs/API.md` 和多用户展示材料为准。

## 1. 系统定义

### 1.1 项目名称

校园多源消息智能聚合与信息管理系统（UniBrief）。

### 1.2 任务陈述

系统面向校园场景中分散、冗余且难以追踪的群聊和通知消息，将不同平台的原始消息统一导入，通过真实 OpenAI-compatible AI 判断消息是否有用，完成摘要、重要度评估、分类、标签和时间识别，并将有价值的信息以关系模型保存。用户可以浏览、搜索、筛选、查看事项、追溯原始来源和查看统计结果。

### 1.3 核心目标

1. 统一保存多平台、多渠道的原始消息及附件元数据。
2. 从闲聊中识别课程、竞赛、活动、行政等有价值信息。
3. 将 AI 结果转化为经过校验的结构化数据，而不是只展示模型文本。
4. 聚合同一事项的多条消息，并保留创建、补充、更新、纠正关系。
5. 将时间信息转化为可管理的 Event。
6. 提供查询、筛选、追溯和至少三类统计。
7. 通过数据库约束、索引、事务和高级对象体现数据库课程设计要求。

## 2. 问题域分析

### 2.1 当前问题

| 问题 | 直接影响 | 系统应对 |
|---|---|---|
| 消息分散在多个平台与群聊 | 用户需要逐个平台翻找 | Platform、Channel 统一建模，Adapter 统一输入 |
| 闲聊和重复提醒数量大 | 重要消息容易被淹没 | AI 有效性判断，Message 状态区分有效、忽略和失败 |
| 自然语言缺少结构 | 难以按重要度、分类和截止时间筛选 | AI 严格结构化输出，InformationItem、Category、Tag、Event 入库 |
| 同一事项多次通知 | 内容重复且可能更新或纠正 | Message 与 InformationItem 多对多，relation_type 表达演化 |
| 摘要可能不准确 | 用户无法验证来源 | 原始 Message 永久保留，信息详情展示所有关联消息 |
| 导入和 AI 服务可能失败 | 重复数据、数据丢失或半成品 | 唯一约束、幂等导入、分段事务、失败可重试 |
| 数据多但缺少整体视角 | 无法判断高价值渠道和信息主题 | 渠道有效率、分类分布、热门标签、截止事项统计 |

### 2.2 系统价值

系统不是消息平台的替代品，而是消息进入之后的信息治理层。它把一次性聊天内容转化为有来源、有关系、有状态、有时间属性的数据库记录。

## 3. 系统边界

### 3.1 系统范围内

- Platform、Channel、Sender 主数据管理；
- JSON、CSV 或模拟 Adapter 消息导入；
- Message 与 MessageAttachment 保存和查询；
- 真实 OpenAI-compatible AI 配置检查、模型列表、手工模型 ID 和连接测试；
- 单条与批量 AI 分析；
- AIAnalysis 持久化；
- InformationItem 创建、关联、更新、人工修正和归档；
- Category 与 Tag 归一化及筛选；
- Event 创建、状态和截止时间查询；
- 原始消息来源追溯；
- 渠道、分类、标签和事项统计；
- 中文 Web 界面。

### 3.2 系统范围外

- 用户注册、登录、权限、User 和 UserFeedback；
- QQ、微信、钉钉私有协议逆向；
- 自动回复和消息发送；
- 多 Agent、RAG、向量数据库；
- 复杂 OCR 和完整附件文件服务；
- 移动端 App；
- 真实个人聊天数据收集。

### 3.3 前提与依赖

- 外部采集工具或合成数据能够提供统一字段：平台、渠道、发送者、外部消息 ID、正文、发送时间及可选附件元数据。
- MySQL 8.x 可用，字符集为 utf8mb4。
- 服务端配置真实 OpenAI-compatible API 的 Base URL、API Key 和模型 ID。
- 第三方 AI 服务可能不支持 `/models`，因此模型 ID 不能只依赖下拉列表。

## 4. 参与者与干系人

|---|---|---|
| 系统使用者/信息管理者 | 主参与者 | 导入消息、配置来源与 AI、分析、查询、追溯、修正信息、查看事项和统计 |
| 消息导入适配器 | 外部系统 | 将不同来源消息转换为系统统一格式并提交 |

## 5. 功能需求

### 5.1 来源管理

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-S01 | 系统应维护 Platform 的名称、类型和状态 | Must | 平台名称唯一，可查询 |
| FR-S02 | 系统应维护 Platform 下的 Channel | Must | 同一平台 external_id 唯一 |
| FR-S03 | 系统应识别并归一化 Sender | Must | 同一平台 external_id 唯一 |
| FR-S04 | 已被 Message 引用的来源主数据不得随意物理删除 | Must | 外键阻止破坏历史或采用受控停用 |

### 5.2 消息导入与原文管理

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-M01 | 系统应支持 JSON 导入，CSV 可作为同级实现 | Must | 合法数据可批量进入 Message |
| FR-M02 | 导入时应自动建立或匹配 Platform、Channel、Sender | Must | 重复主数据不会被再次创建 |
| FR-M03 | 系统应防止同一渠道的同一外部消息重复导入 | Must | 重复导入不增加 Message 数 |
| FR-M04 | 系统应保存正文、发送时间、接入时间和处理状态 | Must | 可查看完整原文和状态 |
| FR-M05 | 系统应保存图片、PDF、Word 等附件元数据 | Must | 附件与 Message 有真实外键 |
| FR-M06 | 用户应能按平台、渠道、发送者、时间、状态、关键词分页查询消息 | Must | 组合过滤和服务端分页可用 |

### 5.3 AI 配置与分析

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-A01 | 系统应读取服务端 AI Base URL、Key 状态、默认模型和超时配置 | Must | 不返回真实 API Key |
| FR-A02 | 系统应从真实 `/models` 获取模型列表 | Must | 支持时返回排序后的模型 ID |
| FR-A03 | `/models` 不可用时应允许手工输入模型 ID | Must | 不因列表失败阻止分析 |
| FR-A04 | 用户应能用选定模型发起真实连接测试 | Must | 返回状态和请求耗时 |
| FR-A05 | 用户应能对单条或一批 Message 指定模型分析 | Must | 实际模型名写入 AIAnalysis |
| FR-A06 | AI 返回必须经过严格 Pydantic 校验 | Must | 非法 JSON 或缺字段不能写业务数据 |
| FR-A07 | 系统应区分认证、模型、限流、超时、网络、供应商和非法输出错误 | Must | 前端显示清晰错误，可决定是否重试 |
| FR-A08 | AI 失败时不得丢失 Message 或留下半成品 InformationItem | Must | Message 为 FAILED 且可更换模型重试 |

### 5.4 有效信息管理

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-I01 | 无用消息不得生成 InformationItem | Must | AIAnalysis 可记录无用，Message 进入 IGNORED |
| FR-I02 | 有用消息应生成一个或多个结构化信息项 | Must | 模型层允许一条 Message 对应多个 InformationItem |
| FR-I03 | 系统应从近期 ACTIVE 信息中寻找候选并决定 create/link/update | Must | 同一事项的多条消息可聚合 |
| FR-I04 | 每个 Message-InformationItem 关系应记录 relation_type | Must | 支持 CREATE、SUPPORT、UPDATE、CORRECTION |
| FR-I05 | 用户应能按分类、标签、重要度、状态、时间和关键词查询信息 | Must | 服务端分页与组合筛选可用 |
| FR-I06 | 用户应能查看信息的全部关联原始消息 | Must | 从 InformationItem 可追溯 Message |
| FR-I07 | 用户应能人工修正标题、摘要、状态和重要度 | Should | 修改后数据可再次查询 |
| FR-I08 | InformationItem 应通过状态归档，不轻易物理删除 | Must | ARCHIVED 状态可保留历史 |

### 5.5 分类、标签与事项

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-C01 | 系统应提供稳定、粗粒度 Category | Must | Category 名称唯一 |
| FR-C02 | 一个 InformationItem 可属于多个 Category | Must | 通过 information_category 关联 |
| FR-T01 | 系统应提供动态、细粒度 Tag | Must | Tag 名称唯一 |
| FR-T02 | 一个 InformationItem 可拥有多个 Tag | Must | 通过 information_tag 关联 |
| FR-E01 | 有时间属性的信息应生成 Event | Must | event.information_id 为 FK + UNIQUE |
| FR-E02 | 用户应能按状态和截止时间范围查询 Event | Must | 可查看未来 7 天/30 天事项 |
| FR-E03 | 系统应支持 UPCOMING、ONGOING、COMPLETED、EXPIRED、CANCELLED 状态 | Must | 状态值受集中枚举控制 |

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-R01 | 系统应统计各 Channel 总消息数、有效消息数和有效率 | Must | 有效数建议按至少关联一个 InformationItem 的去重 Message 统计，可按时间扩展 |
| FR-R02 | 系统应统计各 Category 的 InformationItem 数量 | Must | 空分类和有数据状态均可展示 |

## 6. 数据需求

### 6.1 核心数据对象

| 数据域 | 数据对象 | 关键内容 | 生命周期要求 |
|---|---|---|---|
| 来源域 | Platform、Channel、Sender | 平台、具体群聊/频道、外部发送者 | 被消息引用后保持稳定，不破坏历史 |
| 原始消息域 | Message、MessageAttachment | 原文、时间、处理状态、附件元数据 | 原始证据优先保留，重复导入受控 |
| 分析域 | AIAnalysis | 实际模型、有效性、重要度、置信度、摘要、原始结果 | 支持同一 Message 多次分析与模型对比 |
| 信息域 | InformationItem、MessageInformation | 标题、摘要、状态及消息证据关系 | 可创建、更新、归档和追溯 |
| 组织域 | Category、Tag 及关联表 | 稳定分类、动态主题 | 去重并支持多对多 |
| 事项域 | Event | 开始、截止、事项状态 | 每个 InformationItem 至多一个 |

### 6.2 数据量要求

- 课程硬性演示要求：实体数据不少于 30 条，关联关系数据不少于 200 条。
- 项目计划演示数据：不少于 1,000 条合成 Message、不少于 30 条 InformationItem、不少于 200 条关联记录。
- 数据必须为合成数据，不包含真实个人聊天记录、Cookie 或平台凭据。

### 6.3 数据保留与删除

- Message 是来源证据，原则上不物理删除。
- InformationItem 通过 ARCHIVED 状态归档。
- Platform、Channel、Sender 被引用后应禁止破坏性删除或采用停用方案。
- 关联表可在父实体按明确策略删除时清理。
- 演示清库仅通过专用 reset/seed 流程执行。

## 7. 业务规则

| ID | 规则 |
|---|---|
| BR-01 | Platform.name 唯一。 |
| BR-02 | Channel 在同一 Platform 内以 external_id 唯一。 |
| BR-03 | Sender 在同一 Platform 内以 external_id 唯一。 |
| BR-04 | Message 在同一 Channel 内以 external_id 唯一。 |
| BR-05 | Message 必须同时关联一个 Channel 和一个 Sender。 |
| BR-06 | Message 可有零到多个附件和零到多次 AIAnalysis。 |
| BR-07 | Message 与 InformationItem 为多对多，关系类型不能为空。 |
| BR-08 | Category.name 和 Tag.name 分别唯一。 |
| BR-09 | InformationItem 与 Category、Tag 分别为多对多。 |
| BR-10 | InformationItem 可没有 Event，但最多只能有一个 Event。 |
| BR-11 | AI 输出通过模式校验前不得写入 InformationItem、关联表或 Event。 |
| BR-12 | AI 调用失败不能回滚已成功导入的原始 Message。 |
| BR-13 | 一次成功结果持久化中的 AIAnalysis、信息、关联、分类、标签、事项和状态应原子提交。 |
| BR-14 | API Key 不写数据库、不回传前端、不出现在日志。 |

## 8. 事务需求

### T1 消息幂等导入

输入：统一格式消息批次。

处理：匹配或创建来源主数据，依据 `(channel_id, external_id)` 判断 Message 是否已存在，新消息写入，重复消息计入跳过数。

一致性要求：同一消息多次导入最终只有一条 Message；批次应返回成功、重复和失败数量。

### T2 单条/批量 AI 分析

输入：Message ID 列表与明确模型 ID。

处理：更新 PROCESSING 并提交；事务外调用 AI；严格校验；成功后用短事务写全部结果。

一致性要求：成功结果全部提交，失败结果全部回滚；原始 Message 始终保留；批量允许逐条报告部分失败。

### T3 信息聚合

输入：已校验的有效 AI 结果和近期 ACTIVE 候选信息。

处理：决定 CREATE、LINK 或 UPDATE，写 MessageInformation 和 relation_type。

一致性要求：不得出现只有 InformationItem 而无来源关系的本次新建结果；重复关联不得重复插入。

### T4 信息查询与来源追溯

输入：筛选条件或 InformationItem ID。

处理：分页返回信息；详情联查 Category、Tag、Event 和关联 Message。

一致性要求：任何详情中的来源都必须对应真实存在的 Message。

### T5 统计查询

输入：默认范围或开始、结束时间。

处理：按统一口径聚合渠道有效率、分类数量、标签热度和截止事项。

一致性要求：统计结果与基础表在同一口径下可复核，空数据返回零或空集合而不是错误。

## 9. 非功能需求

### 9.1 性能

- 目标数据规模 1,000 至 10,000 条 Message 时，所有列表使用服务端分页。
- 高频过滤字段使用组合索引，避免全表扫描作为常态。
- AI 网络等待不占用长数据库事务。
- 统计优先使用 View、等价聚合查询或受控存储过程，避免前端拉取全量数据计算。

当前设计没有给出硬性毫秒指标。实现阶段应通过固定数据集记录 Message 列表和三类统计的实际响应时间，再据此补充可验证指标。

### 9.2 可靠性与健壮性

- 导入幂等，重复消息不造成重复数据。
- AI 的 401、模型不存在、429、超时、网络、供应商和非法输出错误分类处理。
- 数据库写入失败必须 rollback。
- AI 失败后 Message 状态可重试。
- 无用闲聊不生成 InformationItem。
- 空列表、空统计和部分批次失败都有明确返回。

### 9.3 安全性

- API Key 仅存在于服务端环境变量。
- 配置接口只返回 `has_api_key`，不返回 Key。
- 日志不记录 Authorization Header 或完整 Key，异常需要脱敏。
- 仓库不提交真实密钥、Cookie、平台凭据和真实个人聊天数据。
- 本系统为单用户课程项目，不把不存在的账号权限功能作为安全亮点。

### 9.4 易用性

- Web UI 使用中文。
- 模型列表与手工模型 ID 并存。
- 列表具有加载、错误、空数据和分页状态。
- 信息详情能在一个页面看到摘要、分类、标签、事项及原始来源。
- AI 失败提示包含错误类型和重试入口，不只显示“失败”。

### 9.5 可维护性与可测试性

- 后端按 API、Service、Repository、AI、Adapter、DB 分层。
- 数据库变更全部通过 Alembic migration。
- 枚举和状态集中定义。
- 自动化测试可 mock HTTP transport，但产品代码不得提供运行时 MockAIProvider。
- 提供固定合成数据和 reset/seed/verify 流程，使课堂演示可重复。

### 9.6 可扩展性

- 新消息来源通过 Adapter 扩展，不改变核心 Message 模型。
- 新 OpenAI-compatible 服务通过 Base URL 和模型 ID 适配。
- 多对多模型允许未来支持一条消息拆分多个事项。
- 本期不以增加微服务、消息队列或向量数据库作为扩展目标。

## 10. 需求到数据模型追踪

| 需求主题 | 主要表 | 关键约束/机制 |
|---|---|---|
| 多平台来源 | platform、channel、sender | 平台内 external_id 唯一 |
| 原文保存和去重 | message、message_attachment | `(channel_id, external_id)` 唯一、真实外键 |
| 多次 AI 分析 | ai_analysis | `(message_id, analyzed_at)` 索引、记录 model_name |
| 有效信息聚合 | information_item、message_information | M:N、联合主键、relation_type |
| 分类与主题 | category、tag、information_category、information_tag | 名称唯一、两个 M:N |
| 截止事项 | event | `information_id` FK + UNIQUE、deadline 索引 |
| 筛选与统计 | 上述核心表及统计 View/查询 | 组合索引、统一统计口径 |

## 11. 验收场景

1. 同一批消息导入两次，第二次不增加 Message。
2. 一条闲聊经过真实 AI 后不生成 InformationItem。
3. 一条有效通知生成 InformationItem、Category、Tag 和 Event。
4. 后续补充消息关联到已有 InformationItem，relation_type 为 SUPPORT 或 UPDATE。
5. 纠正消息更新有效信息并保留 CORRECTION 来源关系。
6. AI 超时或模型不存在时，Message 仍可查看且能更换模型重试。
7. 从 InformationItem 详情可查看全部原始 Message。
8. 三类统计能从基础数据复核。
9. 演示数据达到实体不少于 30、关系不少于 200。

## 12. 当前需求基线结论

现有设计已经覆盖课程要求中的功能需求、非功能需求、完整业务流程和数据库设计主体。实施前仍需冻结 AI 错误记录字段、Channel/Sender 的停用策略、AI 多信息项动作粒度，以及 Trigger/Stored Procedure 的最终方案。冻结后应同步更新 `docs/DATABASE.md`、ER 图、数据库模型图和 API 文档。
