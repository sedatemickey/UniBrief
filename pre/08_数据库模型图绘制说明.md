# 数据库模型图绘制说明

## 1. 图的定位

数据库模型图用于逻辑设计和物理设计，必须展示实际将落入 MySQL 的 13 张表、主键、外键、唯一约束和关键索引。它与概念 ER 图的区别是：ER 图解释业务关系，模型图证明关系如何通过表和约束实现。

数据库：MySQL 8.x；字符集：utf8mb4；命名：snake_case。

## 2. 图例规范

- `PK`：主键。
- `FK`：外键。
- `UK`：唯一键或唯一约束组成列。
- `IDX`：普通索引组成列。
- `NN`：NOT NULL。
- 联合主键用 `PK(1)`、`PK(2)` 或统一钥匙图标标出顺序。
- 外键连线使用 Crow's Foot，并在子表一侧标 FK 字段。
- 不要假设未在设计文档中确定的 `ON DELETE CASCADE`；删除动作需后续定稿。

## 3. 13 张表的字段框

以下内容可以直接作为手工绘制表框的文字来源。

### 3.1 platform

用途：消息平台。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| UK | name | VARCHAR(64) | NN | 平台名唯一 |
|  | type | VARCHAR(32) | NN | 平台类型 |
|  | status | VARCHAR(32) | NN / ACTIVE | 状态 |
|  | created_at | DATETIME | NN | 创建时间 |

### 3.2 channel

用途：具体群聊或消息渠道。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK, UK(1) | platform_id | BIGINT | NN | -> platform.id |
| UK(2) | external_id | VARCHAR(128) | NN | 平台内渠道 ID |
|  | name | VARCHAR(255) | NN | 渠道名称 |
|  | channel_type | VARCHAR(32) | NN | 群、频道等类型 |
|  | created_at | DATETIME | NN | 创建时间 |

唯一约束：`UNIQUE(platform_id, external_id)`。

### 3.3 sender

用途：外部消息发送者，不是系统用户。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK, UK(1) | platform_id | BIGINT | NN | -> platform.id |
| UK(2) | external_id | VARCHAR(128) | NN | 平台内发送者 ID |
|  | display_name | VARCHAR(255) | NN | 显示名 |
|  | source_type | VARCHAR(32) | NN | 教师、学生、机器人等来源类型 |
|  | credibility | DECIMAL(4,3) | NN / 0.500 | 业务层限制 0 至 1 |
|  | created_at | DATETIME | NN | 创建时间 |

唯一约束：`UNIQUE(platform_id, external_id)`。

### 3.4 message

用途：保存原始消息，是核心大表。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK, UK(1), IDX | channel_id | BIGINT | NN | -> channel.id |
| FK, IDX | sender_id | BIGINT | NN | -> sender.id |
| UK(2) | external_id | VARCHAR(191) | NN | 渠道内消息 ID |
|  | content | TEXT | NN | 原文 |
| IDX | sent_at | DATETIME | NN | 发送时间 |
| IDX | ingested_at | DATETIME | NN | 接入时间 |
| IDX | process_status | VARCHAR(32) | NN / PENDING | 处理状态 |

唯一约束：`UNIQUE(channel_id, external_id)`。

关键索引：

- `INDEX(channel_id, sent_at)`；
- `INDEX(sender_id, sent_at)`；
- `INDEX(process_status, ingested_at)`。

### 3.5 message_attachment

用途：消息附件元数据。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK | message_id | BIGINT | NN | -> message.id |
|  | file_type | VARCHAR(64) | NULL | 文件类型 |
|  | file_name | VARCHAR(255) | NULL | 文件名 |
|  | file_url | VARCHAR(1024) | NULL | 文件地址 |
|  | extracted_text | TEXT | NULL | 可选提取文本 |
|  | created_at | DATETIME | NN | 创建时间 |

### 3.6 ai_analysis

用途：保存某条 Message 的一次成功 AI 分析结果，支持多次分析与模型对比。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK, IDX | message_id | BIGINT | NN | -> message.id |
|  | model_name | VARCHAR(128) | NN | 实际使用模型 |
|  | useful | BOOLEAN | NN | 是否有用 |
|  | importance | TINYINT | NN | 重要度 |
|  | confidence | DECIMAL(4,3) | NN | 置信度 |
|  | summary | TEXT | NULL | 分析摘要 |
|  | raw_result | JSON | NULL | 审计用模型原始结果 |
| IDX | analyzed_at | DATETIME | NN | 分析时间 |

关键索引：`INDEX(message_id, analyzed_at)`。

待定：若失败分析也需要数据库审计，应在实现前明确 status、error_type、error_message 等字段或独立分析尝试表。

### 3.7 information_item

用途：系统最终保留的有效信息，是第二个核心业务表。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
|  | title | VARCHAR(255) | NN | 标题 |
|  | summary | TEXT | NN | 摘要 |
|  | source_type | VARCHAR(32) | NN | 来源类型 |
| IDX | importance | TINYINT | NN | 重要度 |
|  | confidence | DECIMAL(4,3) | NN | 置信度 |
| IDX | status | VARCHAR(32) | NN / ACTIVE | ACTIVE/UPDATED/EXPIRED/ARCHIVED |
| IDX | created_at | DATETIME | NN | 创建时间 |
|  | updated_at | DATETIME | NN | 更新时间 |

关键索引：`INDEX(status, importance, created_at)`。

### 3.8 message_information

用途：Message 与 InformationItem 的多对多证据关系。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK(1), FK | message_id | BIGINT | NN | -> message.id |
| PK(2), FK | information_id | BIGINT | NN | -> information_item.id |
|  | relation_type | VARCHAR(32) | NN | CREATE/SUPPORT/UPDATE/CORRECTION |
|  | created_at | DATETIME | NN | 关系建立时间 |

联合主键：`PRIMARY KEY(message_id, information_id)`。

### 3.9 category

用途：稳定、粗粒度分类。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| UK | name | VARCHAR(64) | NN | 分类名唯一 |
|  | description | VARCHAR(255) | NULL | 分类说明 |

预置建议：课程、竞赛、科研、活动、综测、就业、行政、生活、其他。

### 3.10 information_category

用途：InformationItem 与 Category 的多对多关系。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK(1), FK | information_id | BIGINT | NN | -> information_item.id |
| PK(2), FK | category_id | BIGINT | NN | -> category.id |

联合主键：`PRIMARY KEY(information_id, category_id)`。

### 3.11 tag

用途：动态、细粒度主题标签。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| UK | name | VARCHAR(128) | NN | 标签名唯一 |

### 3.12 information_tag

用途：InformationItem 与 Tag 的多对多关系。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK(1), FK | information_id | BIGINT | NN | -> information_item.id |
| PK(2), FK | tag_id | BIGINT | NN | -> tag.id |

联合主键：`PRIMARY KEY(information_id, tag_id)`。

### 3.13 event

用途：由有时间属性的 InformationItem 生成的事项。

| 标记 | 字段 | 类型 | 可空/默认 | 说明 |
|---|---|---|---|---|
| PK | id | BIGINT | NN | 主键 |
| FK, UK | information_id | BIGINT | NN | -> information_item.id；同时唯一 |
|  | start_at | DATETIME | NULL | 开始时间 |
| IDX | deadline | DATETIME | NULL | 截止时间 |
| IDX | event_status | VARCHAR(32) | NN / UPCOMING | 事项状态 |
|  | created_at | DATETIME | NN | 创建时间 |
|  | updated_at | DATETIME | NN | 更新时间 |

关键约束：`UNIQUE(information_id)`。

关键索引：

- `INDEX(deadline)`；
- `INDEX(event_status, deadline)`。

## 5. 推荐模型图布局

### 5.1 单页总览

- 左侧上方：platform，向右连接 channel；platform 下方放 sender。
- 中间左侧：message，作为来源域连线汇合点。
- message 上方：ai_analysis；下方：message_attachment。
- 中间：message_information。
- 中间右侧：information_item。
- 右上：category 与 information_category。
- 右中：tag 与 information_tag。
- 右下：event。

message 与 information_item 使用最醒目的两种颜色；三个关联表统一使用浅灰或白色，避免抢主实体视觉。

### 5.2 两页拆分

如果全字段无法在教室看清，推荐：

- 模型图 A：来源与分析链，包含 platform、channel、sender、message、message_attachment、ai_analysis。
- 模型图 B：有效信息与组织链，包含 message、message_information、information_item、category、information_category、tag、information_tag、event。第二页保留简化的 message 作为连接锚点。

PPT 主页面可使用只显示关键字段的总览，完整字段图放备份页或报告。

## 6. 唯一约束与业务规则对应

| 唯一约束 | 防止的问题 | 业务范围 |
|---|---|---|
| `platform.name` | 重复平台定义 | 全局 |
| `(channel.platform_id, channel.external_id)` | 同平台同渠道重复 | 平台内 |
| `(sender.platform_id, sender.external_id)` | 同平台同发送者重复 | 平台内 |
| `(message.channel_id, message.external_id)` | 同一原始消息重复导入 | 渠道内 |
| `category.name` | 重复分类 | 全局 |
| `tag.name` | 重复标签 | 全局 |
| `event.information_id` | 一个信息生成多个 Event | InformationItem 内 |
| 三张关联表的联合主键 | 同一关系重复插入 | 关系对内 |

## 7. 索引设计与查询对应

| 索引 | 支持的主要查询 | 字段顺序理由 |
|---|---|---|
| `message(channel_id, sent_at)` | 查看某渠道在时间范围内的消息 | 先等值渠道，再按时间过滤/排序 |
| `message(sender_id, sent_at)` | 查看某发送者在时间范围内的消息 | 先等值发送者，再按时间过滤/排序 |
| `message(process_status, ingested_at)` | 查找待处理/失败消息 | 先按状态筛选，再按接入时间调度 |
| `ai_analysis(message_id, analyzed_at)` | 查看某消息的分析历史 | 先定位消息，再按时间排序 |
| `information_item(status, importance, created_at)` | ACTIVE 信息流按重要度与时间筛选 | 符合主要筛选与排序组合 |
| `event(deadline)` | 截止时间范围查询 | 支持未来 7/30 天范围 |
| `event(event_status, deadline)` | 查询某状态下的临近事项 | 先状态，再时间范围 |

实现后应使用 `EXPLAIN` 验证查询是否实际利用索引，不能只展示“建了索引”。

## 8. 规范化说明

### 8.1 第一范式

- 字段保存单一值。
- Category 和 Tag 不作为逗号分隔字符串写入 InformationItem。
- 附件不作为 JSON 数组塞进 Message，而是独立表。

### 8.2 第二范式

- 三张关联表使用完整联合主键。
- MessageInformation 的 relation_type、created_at 描述一对具体的 Message 与 InformationItem 关系，不只依赖其中一端。

### 8.3 第三范式

- Platform、Channel、Sender 分离，Message 不重复保存平台名、渠道名、发送者名。
- Category、Tag 独立，名称修改不需要更新每条 InformationItem。
- Event 独立，避免大量无时间信息的行出现无意义时间字段。

### 8.4 JSON 使用边界

`ai_analysis.raw_result` 是模型原始结果的审计副本，不用于替代 Category、Tag、Event 或 MessageInformation 等已建模关系，因此不违反“不能用 JSON 偷懒替代关系”的原则。

## 9. 数据库高级对象计划

| 类型 | 名称/方案 | 用途 | 展示价值 |
|---|---|---|---|
| View | `v_upcoming_events` | 查询近期未完成事项 | Event 时间查询与状态过滤 |
| View | `v_channel_effectiveness` | 渠道总消息、有效消息、有效率 | 多表聚合和课堂统计 |
| View | `v_category_statistics` | 各分类信息数量 | M:N 关联聚合 |
| 可选 View | `v_tag_popularity` | 标签使用次数 | 热门主题 Top N |
| Trigger/自动维护 | InformationItem 更新时间维护 | 自动维护 `updated_at` | 数据库级一致性 |
| Stored Procedure | `sp_channel_statistics(p_start, p_end)` | 时间区间内渠道统计 | 参数化统计过程 |

当前这些对象是计划设计。最终是否采用 Trigger 还是 MySQL `ON UPDATE CURRENT_TIMESTAMP`，以及 Stored Procedure 是否落地，应以 Alembic migration 和 `docs/DECISIONS.md` 为准。

## 10. 删除与历史策略

- 原始 Message 是证据，不轻易物理删除。
- InformationItem 使用 ARCHIVED，而不是直接删除。
- 已被 Message 引用的 Platform、Channel、Sender 不得破坏性删除。
- 关联表的级联策略要在迁移中明确，当前设计不能先假定全部 CASCADE。
- Channel、Sender 是否增加 status 字段仍需实现前定稿。
