# PPT 大纲

## 1. 总体建议

- 推荐页数：17 页，适配约 10 分钟。
- 叙事结构：需求分析 -> 系统架构 -> 数据库设计 -> 可靠性与总结。
- 数据库设计页：第 9 至 16 页，共 8 页，占有效内容的一半。
- 评分映射：第 3 至 6 页对应功能需求 10 分；第 7 页和第 16 页中的性能、可靠性、安全内容对应其他需求 5 分；第 9 至 16 页中的概念、逻辑、物理设计对应数据库设计 15 分。
- 重点时长：用例图约 45 秒；ER 图和实体关系约 110 秒；系统架构页只讲约 35 秒。
- 页面原则：每页只讲一个结论；正文不超过 5 个要点；图中的文字应能在教室后排看清。
- 状态原则：本次是设计展示，页面角落可统一标注“设计阶段 / Phase 0”。

## 2. 逐页大纲

### 第 1 页：封面

- 主标题：校园多源消息智能聚合与信息管理系统
- 副标题：需求分析、系统架构与数据库设计
- 信息：课程、姓名、学号、日期
- 视觉建议：使用由多个消息渠道汇入同一数据库的简洁背景，不使用聊天机器人形象作为主体。
- 讲解目的：一句话说明“数据库是核心，AI 是分析模块”。

### 第 2 页：汇报目录

- 01 需求分析
- 02 系统架构
- 03 数据库设计
- 04 可靠性与总结
- 视觉建议：横向四段进度线，数据库设计段适当加宽。

### 第 3 页：项目背景与问题定义

- 信息分散：QQ、微信、钉钉等多渠道。
- 信息过载：有效通知被闲聊淹没。
- 手工成本：摘要、分类、记录截止时间、回看来源。
- 核心矛盾：消息很多，但可管理的信息很少。
- 配图建议：三列“现状 -> 问题 -> 目标”，不要使用长段落。

### 第 4 页：系统目标与边界

- 目标：统一接入、智能识别、结构化保存、事项提醒、查询统计、来源追溯。
- 系统内：JSON/CSV 导入、真实 AI、信息管理、Event、统计。
- 系统外：账号体系、平台协议逆向、自动回复、RAG/向量库、多 Agent、移动端 App。
- 配图建议：系统边界图，中央系统框，左右分别放输入和外部服务。

### 第 5 页：参与者与功能需求

- 参与者：系统使用者、消息导入适配器、OpenAI-compatible AI 服务。
- 功能组：来源、导入、消息、AI、信息、分类标签、事项、统计。
- 主图：用例图。
- 讲解目的：从参与者视角证明功能边界完整。

### 第 6 页：代表性完整业务流程

- 主线：导入 -> 原文入库 -> AI 分析 -> 有效性判断 -> 信息聚合 -> 分类/标签 -> Event -> 展示/统计。
- 异常分支：重复消息跳过；AI 失败保留原文并重试。
- 主图：跨“用户、系统、数据库、AI 服务”的泳道流程图。
- 讲解目的：展示业务闭环，不展开页面操作。

### 第 7 页：性能及其他需求

- 性能：1,000 至 10,000 条消息，服务端分页与索引。
- 可靠性：幂等导入、事务回滚、AI 可重试、原文不丢失。
- 安全性：API Key 仅服务端环境变量，日志脱敏。
- 易用性：中文界面、模型手工输入、错误/空状态清晰。
- 可维护性：分层后端、迁移管理、集中枚举、合成数据。
- 配图建议：五列指标卡或“目标-设计手段”二列表。

### 第 8 页：总体系统架构

- 输入：JSON/CSV/模拟 Adapter。
- 前端：React + TypeScript + Ant Design + TanStack Query + ECharts。
- 后端：FastAPI，Router / Service / Repository / AI Provider / Adapter 分层。
- 数据库：MySQL 8 + SQLAlchemy + Alembic。
- AI：真实 OpenAI-compatible API。
- 主图：分层架构图，MySQL 置于中心或底部主位。

### 第 9 页：数据生命周期与数据库职责

- 来源主数据 -> 原始消息 -> 分析记录 -> 有效信息 -> 分类/标签/事项 -> 查询统计。
- 每一步标注对应表名。
- 主图：数据生命周期/证据链图。
- 讲解目的：从架构自然过渡到数据库设计。

### 第 10 页：数据库概念 ER 图

- 10 个实体表、3 个关联表。
- 先按来源、原始消息与分析、有效信息、组织与事项四组解释 10 类实体职责。
- 重点基数：Platform-Channel、Message-InformationItem、InformationItem-Event。
- 主图：概念 ER 图，只保留主键和少量业务属性。
- 讲解目的：说明实体为何存在，以及 1:N、M:N、1:0..1 的业务含义。

### 第 11 页：核心多对多关系

- 多条 Message 可支持一个 InformationItem。
- 一条 Message 可形成多个 InformationItem。
- relation_type：CREATE / SUPPORT / UPDATE / CORRECTION。
- Category 与 Tag 也分别为 M:N。
- 配图建议：使用“初始通知、补充、纠正 -> 同一信息项”的具体例子，不画新 ER 图。

### 第 12 页：13 表数据库模型总览

- 来源域：platform、channel、sender。
- 消息域：message、message_attachment、ai_analysis。
- 信息域：information_item、message_information。
- 组织域：category、information_category、tag、information_tag。
- 事项域：event。
- 主图：数据库模型图总览；若太密，主模型放大，字段只显示 PK/FK/UK。

### 第 13 页：键、约束与完整性

- 所有实体明确主键和真实外键。
- 去重：Channel、Sender、Message 的复合唯一约束。
- 唯一命名：Platform、Category、Tag。
- 业务约束：Event 的外键 + UNIQUE。
- 关系防重：三个关联表的联合主键。
- 配图建议：约束表格，右侧突出 `event.information_id`。

### 第 14 页：规范化与数据质量

- 1NF：字段原子化，标签不放逗号字符串。
- 2NF：关联表属性依赖完整联合主键。
- 3NF：来源、发送者、分类、标签独立建表，减少传递依赖。
- JSON 边界：只保存 AI 原始审计结果，不替代关系建模。
- 历史保留：Message 不轻易删除，InformationItem 使用 ARCHIVED。
- 配图建议：“反例 -> 正确表结构”对照表。

### 第 15 页：索引、统计与高级数据库对象

- 索引：Message 两组来源时间索引、处理队列索引；Information 状态重要度索引；Event 截止时间索引。
- View/统计：渠道有效率、分类分布、热门标签、未来截止事项。
- Trigger/自动维护：维护 `information_item.updated_at`。
- Stored Procedure 计划：`sp_channel_statistics(p_start, p_end)`。
- 配图建议：左侧“查询 -> 索引”映射，右侧四个统计小图占位。

### 第 16 页：事务、可靠性与安全

- 分段事务：Message 入库、AI 外部调用、结果短事务。
- 回滚原则：失败不产生半成品 InformationItem。
- 可重试状态：PENDING / PROCESSING / PROCESSED / FAILED / IGNORED。
- AI 错误：认证、模型、限流、超时、网络、非法输出。
- 安全：Key 不入库、不回传、不记录。
- 主图：AI 分析时序图或事务边界图。

### 第 17 页：总结与后续验证

- 原始消息不丢失。
- 结构化信息可聚合、可追溯。
- 关系和约束由数据库真实保证。
- AI 输出必须校验，失败可恢复。
- 后续：迁移 -> 实现 -> 测试 -> 合成数据 -> 系统演示。
- 结束语：AI 负责理解消息，数据库负责让信息长期可信。

## 4. 页面设计规范

- 标题 28 至 34 pt，正文不低于 18 pt，图中表名不低于 16 pt。
- 一个页面最多使用两级文字层次。
- 数据库表按领域固定配色，但避免整套页面只用同一蓝色系。
- 关联表使用中性色，实体表使用较强颜色，主业务表 Message 和 InformationItem 使用强调色。
- 关系线尽量横平竖直，避免穿过表框；所有基数标注统一使用 Crow's Foot 或统一文字，不混用。
- 不在图旁重复整段解释，页面只留结论，完整话术放在演讲备注中。
