# 业务流程图绘制说明

推荐至少手工绘制一张“消息导入到信息展示”的主泳道图。另三张流程图可用于报告或答辩备份：导入去重、信息聚合决策、AI 失败与重试。

## 1. 图 A：代表性完整业务流程

### 1.1 图的目的

展示课程第二次演示也会采用的完整业务闭环，但本次只讲设计：消息如何进入数据库、如何经过真实 AI、如何形成结构化信息，以及异常时如何保护数据。

### 1.2 泳道

从左到右或从上到下使用四条泳道：

1. 系统使用者 / Web 前端
2. FastAPI 与业务 Service
3. MySQL 数据库
4. OpenAI-compatible AI 服务

Adapter 可画在开始节点旁作为外部输入，不必单独占一条泳道。

### 1.3 节点与顺序

| 序号 | 泳道 | 节点类型 | 节点文字 | 后续 |
|---:|---|---|---|---|
| 1 | 用户 | 开始 | 选择 JSON/CSV 消息文件 | 2 |
| 2 | 前端/服务 | 处理 | 校验统一输入格式 | 3 |
| 3 | 服务 | 处理 | 归一化 Platform、Channel、Sender | 4 |
| 4 | 数据库 | 判断 | `(channel_id, external_id)` 是否已存在？ | 是到 5，否到 6 |
| 5 | 服务 | 处理 | 记为重复并跳过 | 7 |
| 6 | 数据库 | 数据写入 | 写入 Message，状态 PENDING；写附件元数据 | 7 |
| 7 | 前端 | 处理 | 返回新增、重复、失败数量 | 8 |
| 8 | 用户 | 处理 | 选择模型，发起单条或批量分析 | 9 |
| 9 | 数据库 | 数据写入 | Message -> PROCESSING，并提交 | 10 |
| 10 | 服务/数据库 | 处理 | 查询近期 ACTIVE InformationItem 候选 | 11 |
| 11 | AI 服务 | 外部处理 | 分析消息并返回结构化 JSON | 12 |
| 12 | 服务 | 判断 | 调用成功且 Pydantic 校验通过？ | 否到 13，是到 14 |
| 13 | 数据库 | 数据写入 | Message -> FAILED，记录错误分类，可重试 | 25 |
| 14 | 服务 | 判断 | `useful` 是否为 true？ | 否到 15，是到 16 |
| 15 | 数据库 | 短事务 | 写 AIAnalysis；Message -> IGNORED 并提交 | 25 |
| 16 | 服务 | 判断 | 动作是 create / link / update？ | 分别到 17、18、19 |
| 17 | 数据库 | 短事务步骤 | 新建 InformationItem | 20 |
| 18 | 数据库 | 短事务步骤 | 关联已有 InformationItem | 20 |
| 19 | 数据库 | 短事务步骤 | 更新已有 InformationItem | 20 |
| 20 | 数据库 | 短事务步骤 | 写 MessageInformation 与 relation_type | 21 |
| 21 | 数据库 | 短事务步骤 | 归一化并关联 Category、Tag | 22 |
| 22 | 服务 | 判断 | 是否存在时间属性？ | 是到 23，否到 24 |
| 23 | 数据库 | 短事务步骤 | 创建或更新 Event | 24 |
| 24 | 数据库 | 提交 | Message -> PROCESSED，提交完整短事务 | 25 |
| 25 | 前端 | 处理 | 信息流/事项/统计刷新 | 26 |
| 26 | 用户 | 处理 | 查看信息详情并追溯原始 Message | 27 |
| 27 | 用户 | 结束 | 完成一次信息处理闭环 | 结束 |

### 1.4 图上必须标出的事务边界

- 节点 6：原始 Message 入库事务，独立于 AI 调用。
- 节点 9：PROCESSING 状态更新后立即提交。
- 节点 11：外部 HTTP 调用，明确标注“事务外”。
- 节点 15 或 17 至 24：结果持久化短事务。
- 若节点 17 至 24 任一步失败：指向“整体 rollback -> 独立事务写 FAILED”，不要直接连到 PROCESSED。

### 1.5 图上应突出的一句话

> 原文先入库，AI 在事务外调用，结构化结果在短事务中原子提交。

## 2. 图 B：消息导入与幂等去重流程

### 2.1 节点

1. 接收一条统一格式消息。
2. 校验必填字段：平台、渠道 external_id、发送者 external_id、消息 external_id、content、sent_at。
3. 按 Platform.name 查找或创建 Platform。
4. 按 `(platform_id, channel.external_id)` 查找或创建 Channel。
5. 按 `(platform_id, sender.external_id)` 查找或创建 Sender。
6. 按 `(channel_id, message.external_id)` 查询 Message。
7. 若已存在：标记本条为 duplicate，不写新 Message。
8. 若不存在：写入 Message，状态 PENDING；写零到多个 MessageAttachment。
9. 若并发下唯一键冲突：按重复数据处理，不生成第二条记录。
10. 汇总批次 inserted、duplicate、failed 数量。

### 2.2 绘图重点

- 判断菱形中直接写唯一键，不写模糊的“是否重复”。
- 将“应用层先查询”和“数据库唯一约束兜底”都画出来，说明幂等不是只靠 if 判断。
- 批量导入的单条失败策略在实现前需要定稿；图中可用注释写“返回逐项结果，避免一个坏记录掩盖整批原因”。

## 3. 图 C：InformationItem 聚合决策流程

### 3.1 输入

- 当前 Message；
- 已校验的 AI 结构化结果；
- 最近有限数量的 ACTIVE InformationItem 候选。

### 3.2 节点

1. 从 AI 结果提取标题关键词和主题。
2. 从近期 ACTIVE 信息中按时间、关键词或简单相似规则形成候选集。
3. 将 Message 与候选摘要交给真实 AI 选择动作。
4. 判断动作：
   - `create`：新建 InformationItem，relation_type 通常为 CREATE；
   - `link`：不改核心内容，只新增关系，relation_type 通常为 SUPPORT；
   - `update`：更新已有信息并新增关系，relation_type 为 UPDATE；
   - 若内容纠正原通知：关系类型为 CORRECTION。
5. 归一化 Category 和 Tag，避免同名重复。
6. 如果含时间属性，创建或更新唯一 Event。
7. 统一提交。

### 3.3 示例标注

可在图旁放一个三条消息的例子：

- M1：“数据库课设选题周五前提交” -> 创建 I1。
- M2：“提交格式为 PDF，发给学习委员” -> 支持并更新 I1。
- M3：“截止时间改为下周一 18:00” -> 纠正 I1 并更新 Event。

图旁结论：三条原文全部保留，但信息流中只展示一个不断演化的 I1。

## 4. 图 D：AI 失败与更换模型重试流程

### 4.1 节点

1. 用户选择模型并发起分析。
2. Message 从 PENDING 或 FAILED 进入 PROCESSING。
3. 调用 AI 服务。
4. 判断错误类型：
   - AUTH_ERROR：提示检查服务端 Key；
   - MODEL_NOT_FOUND：允许选择或手工输入其他模型；
   - RATE_LIMITED：提示稍后重试；
   - TIMEOUT / NETWORK_ERROR：允许重试；
   - PROVIDER_ERROR：显示供应商错误摘要；
   - INVALID_AI_OUTPUT：提示输出未通过结构校验。
5. Message -> FAILED，原文与附件不变。
6. 确认没有新建半成品 InformationItem。
7. 用户修改模型或稍后重试。
8. 成功后进入正常结果持久化流程。

### 4.2 绘图重点

- 错误分支最后都回到“可重试”，但 AUTH_ERROR 需要先修复服务端配置。
- 不画“返回模拟结果”分支。
- 明确错误信息不会包含 API Key。

## 5. 图 E：第二次课堂演示流程预告

这张图可不放在第一次 PPT，仅在结尾用一行说明后续如何验证设计：

1. 导入固定合成数据。
2. 展示重复导入结果。
3. 加载或手工输入真实模型并测试连接。
4. 分析一批消息。
5. 展示闲聊过滤、信息聚合、Category、Tag 和 Event。
6. 从信息详情追溯原文。
7. 展示三类统计。
8. 演示一次模型错误或超时后的重试。

## 6. 绘图规范与自检

- 开始/结束使用圆角终止符，处理使用矩形，判断使用菱形，数据库写入可用圆柱或带数据标记的矩形。
- 正常路径使用实线，异常路径使用另一种颜色或虚线；不要只依赖红绿色区别。
- 所有判断出口标注“是/否”或具体动作。
- 泳道表达责任主体，数据库不能替代业务 Service 做 AI 决策。
- 同一张图不同时解释架构层次、数据表字段和页面布局。
- 图中每个数据库写入步骤至少能对应一张已设计的表。
